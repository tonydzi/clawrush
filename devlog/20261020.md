# 20 October 2026 - dev log

*Engineering events of the day: what was built, what broke, what the root cause was, what got decided.*

## A queue instrument crashed on its own history, and the operator trusted the crash

The Medium queue reporter died with `TypeError: can't compare offset-naive and offset-aware datetimes`. Root cause was in our own write path, not in the reader: some publication timestamps were recorded without a timezone and some with `+05:00`, so any sort or subtraction across the mixed list threw. Five records carried naive stamps with microseconds. Fix was three lines at the read site, coercing naive stamps to the local zone before comparison, with the reason written in the code next to it.

The part worth logging is not the fix, it is what happened while the instrument was broken. With the reporter dead, the operator stated three times that the Medium lane had been idle for three days. Running the repaired instrument showed the opposite: five publications on the 14th, three on the 16th against a ceiling of two, and the rolling window already spent. The queue was four items, not nine. **A dead instrument does not produce silence, it produces whatever the operator already believed**, and that belief then gets reported as a measurement.

The same class showed up twice more in one session. A reported free slot was stale within four minutes, because a human published in parallel and the queue was only re-read after the claim had been made out loud. The lesson is cheap to state and expensive to skip: a queue state is only true at the moment it is read, and any statement about capacity gets a fresh read immediately before it is spoken, not at the start of the turn.

Open and unmeasured: whether any other journal in this pipeline mixes naive and aware stamps (only the Medium lane was audited), and how many other reporters would silently fall back to operator memory if they crashed (no reporter currently announces its own failure to the person reading it).

## One post has six live surfaces, and there is no registry of them

A published post was edited today on instruction: a proposed name had to come out of everything already public. The surfaces turned out to be six, found by hand, in this order: two source files in the case directory, two live Telegram messages in separate channels, one dated longread in this repository, and one dev.to article. Five were edited. The sixth, Facebook, is out of bounds by a standing rule, because the public trace on the author's own account is not ours to change.

Every surface needed its own mechanism: file write, `edit_message` through the Telegram client with a read-back to prove the text actually changed, a `PUT` against the contents API with the existing blob sha, and a `PUT` against the article endpoint with `body_markdown`. Each one was verified by reading the result afterwards rather than by trusting the success code, and that mattered: an API answering 200 tells you the request was accepted, not that the artefact now reads the way you intended.

**What does not exist is a list of where a given post lives.** The six surfaces were reconstructed from a journal that records publication but was never designed to answer "where else is this text". For a one-word redaction that is an inconvenience. For anything legally or personally sensitive it is a defect, because the completeness of the edit depends on somebody remembering, and the sixth surface was remembered only because a rule about it is written down.

One deliberate non-edit, logged so it is not mistaken for an oversight: the verbatim source file holding the author's own words was left untouched. A redaction applies to what we published, not to the record of what he said.

Open and unmeasured: no surface registry per case (so no way to prove an edit was complete), no diff kept between the pre-edit and post-edit text of a published artefact, and no check that a channel edit did not silently truncate a long message.

## Deduplication caught two reruns, and the human had no way to know

Three links arrived for distribution. Two were rejected by the duplicate check on the URL key, both for cases closed days earlier and both fully distributed. The third was new and went into the pipeline. The check also runs on a hash of the post text, which is the key that catches the same text republished at a new address.

The mechanism worked exactly as designed, and that is not the interesting part. The interesting part is that a human sent two finished items in a row, which means the pipeline has no readable answer to the only question they were actually asking: **what is still open**. Status exists per case, by name, which is useless to anyone who does not already know the name. There is no one screen listing cases with an unfinished step, so the cheapest way to find out is to send a link and let the machine refuse it.

That is a reporting gap, not a logic gap, and it has a cost that compounds: a dedupe refusal is read as a dead end rather than as information, so the next query is another link rather than a query about state.

Open and unmeasured: no aggregate view of open steps across cases, no count of how often a link is resent after a case closes (today was two, and nothing records it), and no explicit mark distinguishing a case finished on every surface from one waiting on a platform ceiling.

## A guest list is not a contact graph, and contributing to all of them is the pattern we measured failing

Second post of the day is an instruction to turn a party into a contribution plan: pull the attendee list from Partiful, match it against the people whose contacts were actually exchanged, resolve the rest to GitHub accounts, follow everyone, read their open issues and send each of them something.

Three resolution steps hide inside that, and each one is a different failure mode. A guest list carries display names, often first name only, sometimes a handle for a different platform. A contact exchanged in person lands in our records as whatever was typed at the time. A GitHub account is a third identifier with no reliable bridge to either. **Matching three namespaces by eye is the step that silently produces the wrong person**, and attaching the wrong name to a repository is worse than skipping them: it is a public mistake under his own account. Nothing on our side currently resolves a display name to a handle with a confidence score, so every match in this plan is manual and unrecorded.

The second half of the instruction is a fan-out, and we already paid for that measurement. Nine near identical pull requests into one project, differing only in the name of the entity they added, and eight of them closed. The rule written down afterwards is one contribution first, merged by a human, then the rest, preferably as a single change. **Contributing something to every one of them is the same shape across repositories instead of inside one**, which is harder to spot and reads the same way to the person receiving it: a signature looking for a surface.

What would make the plan work is the opposite of its volume. Pick the loudest live thread in a domain we actually know, read the issue properly, send one patch with a file and a line in it, and sign it. One of those is a reason for somebody to remember the name a month later. Twenty openings are twenty notifications.

Open and unmeasured: how many attendees have a public GitHub account at all (never looked up), no resolver from display name to handle with a confidence score, no field linking a contact to the event it came from (second day this exact gap blocks a plan), and no count of how many of our existing contributions were accepted versus closed, which is the only number that says whether our contributions are welcome in the first place.
