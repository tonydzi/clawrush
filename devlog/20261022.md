# 22 October 2026 - dev log

*Engineering events of the day: what was built, what broke, what the root cause was, what got decided.*

## Compress before you index, because a wrong distillate is visible and a bad embedding is not

Today's post describes the retrieval design we actually run: every session, from coding rails and from browser rails, lands in the vault, and each one is reduced to a few sentences saying what it was about, what pain it closed and what was achieved. New sessions search those sentences rather than the transcripts.

Worth logging because the compression is usually justified as a cost measure and the real argument is accuracy. Embedding a 40-page transcript produces a vector dominated by whatever the conversation talked about most, which is rarely what it concluded. Retrieval then returns the longest session that mentioned your words. A three-sentence distillate carries the conclusion and nothing else, so similarity is computed against the answer rather than against the surrounding noise.

The second property is operational and matters more over time. **A wrong distillate is readable, a bad embedding is silent.** If the summary says the session was about something it was not, a human notices in one glance; if a transcript embedded badly, nothing ever surfaces and nobody learns why. That makes the summary layer auditable in a way the vector layer is not, and it is the only part of this pipeline a person can check by eye.

What has never been sampled is whether the distillates are right. Nobody has taken twenty sessions, read the original and the summary, and counted how often the summary names the wrong pain or the wrong outcome. That error does not announce itself: a wrong distillate stays in the index and quietly answers future questions with the wrong session.

Open and unmeasured: distillate accuracy (zero samples), whether the fixed three-question shape loses sessions that solved several unrelated things, and whether a session that ended in failure gets distilled as a failure or silently as the attempt.

## The recall hit rate is the number the whole design rests on, and it does not exist

The post states the mechanism: every new session first tries to work out whether we have worked on this topic before, and very often the knowledge was already in storage. The example is twenty to thirty repetitions of the same meetup question in one week.

That example is well chosen, because it is the case where recall genuinely beats a fresh search. The right answer depends on which events were already recommended and already registered for, and a stateless assistant cannot know either, so it would re-derive from the public web every time and give the same answer twice.

What is missing is the number that would make the claim checkable. **Nobody has measured how often the lookup finds the earlier session and how often it misses and the work gets redone.** The measurement is cheap and well defined: assemble thirty questions whose answers provably exist in previous sessions, run each as a fresh session, and count how many surface the right prior. That gives a hit rate, and a hit rate is the only form in which "very often" can be reported to anyone.

There is a second failure mode behind the first, and it is worse because it is invisible from inside. A miss looks exactly like a new question: the session simply starts working, does the research again, and produces a plausible answer. Nothing in the pipeline flags "I looked and found nothing", so the cost of a miss is paid silently in duplicated work. A counter on lookups-with-no-hit would expose it, and we do not have one.

Open and unmeasured: recall hit rate against known priors (zero samples), no counter for lookups that returned nothing, and no record of duplicated work, so the saving the design is supposed to produce has never been quantified in either direction.

## Shared memory between your machines is a filesystem problem, between people it is not

The post ends with the cross-machine half: ask on one computer, walk away, ask on another, and the second one sees the earlier conversation because the machines share one memory area. A session can start on one machine and finish on another.

Logged because it is accurate and because the boundary is drawn correctly this time, which was not true earlier in the week. Machines belonging to one owner share state through a synced vault, and that is a solved problem with a known shape: one writer per surface, conflict rules, and a human who decides what wins. The thing that makes it work is not the transport, it is single ownership.

Between people none of that holds, and the failure is not technical either. Two independently owned vaults do not merge, because there is no one to resolve a conflict and no shared canon to resolve it against. It is worth keeping these two sentences adjacent in our own writing, since the distance between them is where most of this week's optimism lived.

One operational note from this node, recorded so nobody repeats the check. The engine that builds the session index exists in the vault and is readable here, but the index itself is deliberately not synced to this machine, because the vector files are excluded by design and the search lives where the GPU is. So from this node the corpus size cannot be read at all, and any claim about how many sessions are indexed has to come from the hub. **A claim that can only be verified on one machine is a claim this machine must not make**, and today it was marked as such rather than guessed.

Open and unmeasured: no cross-machine freshness check on the index (a stale vault on one node looks identical to an up-to-date one from the inside), and no per-node report of what the index actually contains.

## Self-rewriting is mandatory only where the environment moves, and nothing counts the rewrites

Second post of the day states a rule: every routine is obliged to notice what it tripped over, fix that, and rewrite itself for next time. The examples are job boards whose formats change and APIs or MCP endpoints that fall off, and in that class the rule is right for a reason worth stating precisely: the routine's failure rate is driven by somebody else's changes, so a fixed implementation decays whether or not anybody touches it.

The part that needs narrowing is the word every. A routine reading a stable local file has no decay source, and granting it permission to rewrite itself adds a failure mode it did not have. **Self-modification is a cure for environmental drift, not a virtue**, and applying it where there is no drift is how a working script acquires a bug. The honest form of the rule: mandatory for routines whose inputs are owned by someone else, optional elsewhere.

What does not exist on our side is any accounting of the rewrites. Nothing counts how many self-edits have happened, nothing records what each one changed, and nothing compares the routine's success rate before and after. That means the strongest claim in the post, that this really does cut the time spent keeping infrastructure alive, has no before-and-after behind it. **A self-improving routine with no edit log is indistinguishable from a drifting one**, because the only evidence either way is whether it still works today.

Two cheap instruments would close it. One: a line per self-edit with what broke, what changed, and the run that triggered it, which also makes the edits reviewable by a human. Two: a per-routine success counter sampled over the ten runs before and the ten after, which answers whether the rewrite helped or just moved the failure.

The model claim is in the same state. Allegedly this works well on the stronger models and poorly on the weaker ones, which is plausible, and no routine here has ever been run on two models side by side with the same failures injected. That is a shadow comparison somebody could run in an afternoon, and it would convert a preference into a routing rule.

Open and unmeasured: no count of self-rewrites, no edit log, no before-and-after success rate per routine, no side-by-side model comparison, and no guard against a routine rewriting itself into a worse version with nobody noticing until output stops.

## The routine count is a fleet claim, and this node can only see 58

Logged because it is a claim this machine cannot verify and the post states it loosely on purpose.

The post says getting on for a hundred routines, maybe two hundred, maybe three hundred, and admits the count was never done. Read live on the node this file is written from: 58 scheduled tasks outside the system folder. The rest of the estimate covers six machines plus cron on the non-Windows nodes, and a per-node sum has not been taken today.

The reporting rule we keep relearning applies here: a number that can only be assembled on another machine is not this machine's number. Either the fleet registry is queried and the sum quoted with its date, or the local figure is given and labelled local. Both are honest; a confident three hundred from a node that can see 58 is not.

Open and unmeasured: no fleet-wide routine count taken today, and no freshness marker on the live routine registry, so the gap between the registry and reality is unknown in either direction.

## A party conversation is not a policy, and the difference matters when people act on it

Third post of the day carries a practical claim many readers will act on directly: four subscriptions are safe, enforcement starts somewhere near a thousand accounts, and putting your subscription account into third-party harnesses is fine. The source is named honestly in the post itself, five to seven employees at a Founder House event, laughing, at a coworking space in San Francisco.

Logged because the provenance is the whole finding. **Friendly words at a party are evidence about mood, not about enforcement**, and the two differ in exactly the cases that matter: automated systems act on signals the people you met do not control, and nothing said over a drink changes what a rate limiter does at 3am. The post does hedge, and the hedge is his, which is why nothing was softened in the text.

What we can check on our own side is narrower and worth recording. We run multiple accounts across several rails and have never been restricted, which is one datapoint consistent with the claim and useless as proof of it, because the same observation is what every unbanned user has the night before. No account-level enforcement event has occurred on this fleet, so our evidence is an absence.

The actionable version for anyone reading our logs: treat the number as unverified, keep each vendor's current terms as the authority, and if a workflow depends on account volume, build it so a single revocation degrades it rather than stops it. We do not currently have that property written down as a requirement anywhere, which is the real gap this post exposes in our own setup.

Open and unmeasured: no record of what each vendor's terms actually say about third-party clients as of today, no fallback design for a revoked rail inside the harness we run, and no monitoring that would tell us a rail had been throttled rather than merely slow.

## If model convergence is the premise, nothing we built depends on it being right

The post's strategic claim is that mass-market models converge to within 5 to 10 percent and the differentiator moves to the interface holding several of them. Logged as a forecast, because it is one, and because it is worth stating what happens to our own work under either outcome.

If convergence holds, the layer we build is the product, and routing between interchangeable models is a pure interface problem. If it does not hold, and frontier models keep separating on reasoning while cheap ones commoditise, then the same layer becomes a router that has to know which model is good at what, which is a harder and more valuable problem. **Either way the work is the same shape, which is the only reason the premise does not need to be settled before building.**

The engineering note worth keeping is about what that means for our model routing. Today the choice of model per task is written by hand in a config and judged by feel. Under the second scenario that config is the product; under the first it collapses to a cost table. Nobody has measured our own spread: no task here has been run across the rails we have with the same input and the outputs compared, so we have no in-house evidence for or against convergence while publishing a view on it.

Open and unmeasured: no same-input comparison across available rails, no per-task quality record that would let a router choose on evidence, and no cost-per-task table, which is the artefact needed under either outcome.
