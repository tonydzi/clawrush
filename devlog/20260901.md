# 1 September 2026 - dev log

## Rule-to-door binding

Problem statement: a written rule that no code path invokes has no effect on behaviour, but is indistinguishable from an enforced one when you read the rules document. Measured on our own canon: a majority of recently added rules had no caller.

Proposed mechanism, in three parts:

1. **Task taxonomy from history.** Read the last N sessions, cluster into recurring task types. Target is dozens, not ten. Ten types means the clustering is too coarse to attach specific rules to.
2. **Rule binding per type.** Each type carries its own checklist: the rules that apply and the mistakes already made inside that type. Some rules bind to one type, some to all of them.
3. **Classification at intake.** A task arriving gets classified before work starts, and its checklist fires. Classification is the door.

Consequence for context budget: rules currently loaded on every session can move behind their door, loaded only when their type is active. The always-loaded file stops being the only home.

## Distribution engine, state today

Per-case JSON journals, nested by platform. Steps record URL and timestamp at publication. Stop-flag checked inside the send functions themselves, not in the command branch above them, because a branch-level check is bypassed by any other branch that also sends.

Daily GitHub pair: one longread and one devlog per calendar day, named by date, and every post published that day points at the same pair. Stubs are written ahead of time so the link exists before the text does. Posts older than the switch date point at the directory listing instead.

**Gap found today:** stubs for four days were created and never filled, while more than twenty published links pointed at them. The stub mechanism worked, the filling step had no schedule attached to it. Same class as the rules problem above: the mechanism existed, the caller did not.
