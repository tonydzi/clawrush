## Post 1: a skill for making skills, with one algorithm behind all of them

### ⭐⭐ Recall result: three skills for making skills already exist

Checked on this node, `~/.claude/skills`:

| skill | size | mtime | role |
|---|---|---|---|
| `skillify` | 46,716 b | 2026-09-22 | the large one, turns a process into a skill |
| `skill-gap` | 12,280 b | 2026-10-02 | finds the hole where a skill is missing |
| `skill-forge` | 5,899 b | 2026-10-02 | the smith |

Plus `skill-creator` shipped as a plugin on the same shelf.

Three artefacts for one job, built six weeks apart, none of which absorbed the others. That is the first finding, and it is a finding about consolidation rather than about absence.

### ⭐⭐⭐ The measurement that names the problem: a 267-fold spread

`~/.claude/skills`: **282** directories, **277** with a `SKILL.md`, **3,683 KB** total.

| statistic | value |
|---|---|
| median body | **9,315 b** |
| largest | `dr-fanout` **179,104 b** |
| smallest | `screenpipe-worklog` **671 b** |
| ratio | **267 : 1** |

Top five by size: `dr-fanout` 174KB, `apply` 125KB, `tt` 122KB, `retro` 94KB, `rep-reply` 52KB.

There is no stated rule anywhere about how large a skill may be. His brief asks "how broad or detailed should the rules and descriptions be", and that question currently has no answer in the canon, which is precisely why the spread looks like this. "Entropy growth" with a number attached.

### ⭐ Where a rule exists, compliance is 96 percent

Standing rule: a skill description is at most 400 characters, on one quoted line. Instrument: `skill_desc_audit.py`, 12,249 b, live.

Measured across all 277:

- without a `description` field: **0**
- exceeding 400 characters: **13**, which is **4 percent**
- worst offenders: `local-to-call` 1,281, `local-brain-onboard` 1,133, `local-fb-messenger` 1,003, `local-fb-alpha` 965, `local-llm-wave` 884, `local-github-growth` 861

⚠️ All 13 are `local-` skills, meaning node-local rather than fleet-wide. So the drift is concentrated where the fleet-wide audit has least reach, which is a useful pointer for whoever runs the cleanup.

**Class worth naming:** the dimension with a rule and a door drifts at 4 percent. The dimension with no rule drifts 267-fold. That is the whole argument for writing the methodology, and it is a measurement rather than an opinion.

### ⭐ Two further instruments already stand beside the shelf

- `skill_usage_log.py`, 13,442 b: counts whether a skill is *used*, not merely invoked.
- `codex_skills_bridge.py`, 18,109 b: mounts one file for a second agent instead of copying it.

Combined with the three creators and the description auditor, the "one clear algorithm" already has a creator, a gap-finder, an auditor, a usage counter and a cross-agent bridge. The missing part is a single page stating size, required sections, and the split-versus-grow rule.

### ⚠️ Cheapest input to the methodology needs no research order

A 3.6MB shelf of 277 skills is the standing context tax on every session.

His question "which types of skills are better to create" has a local answer available today: run `skill_usage_log.py` over the last 30 days and list which of the 277 were used at all. Types that never fire do not need a design standard, they need deleting. That measurement costs nothing and sharpens the external research rather than replacing it.

### Open, in order of payoff

1. Run the usage counter over 30 days and split the 277 into used, called-but-unused, and cold.
2. Write the one page: maximum body size, required sections, when to split.
3. Decide whether `skillify`, `skill-forge` and `skill-gap` become one skill or stay three with stated boundaries, since three creators for one job is the same drift the page is meant to stop.
4. Fix the 13 descriptions over 400 characters, all of them local.
5. Only then commission the external research, with the local numbers already in hand.

### ⚠️⚠️ Instrument warning: mtime is not an edit history

Grouped by month:

| month | files | share |
|---|---|---|
| 2026-06 | 168,026 | 58.8% |
| 2026-07 | 46,512 | 16.3% |
| 2026-09 | 41,351 | 14.5% |
| 2026-08 | 19,595 | 6.9% |
| 2026-10 | 9,835 | 3.4% |
| 2026-11 | 409 | 0.1% |

A single month holding 168 thousand files is a deployment timestamp, not a working rhythm.

Defensible claim: **851 files changed in the last 30 days**, measured directly. Not available from this instrument: "these files never change". What mtime supports is "unchanged since they landed on this disk". Sufficient for the architectural decision, insufficient to quote as a change-frequency statistic, and the difference matters because the second phrasing invites a per-file prediction rule that the data cannot justify.

### ⭐⭐ The session store is the mirror image, and that is where the rule lives

`~/.claude/projects`: **942** `.jsonl` session files, **873** changed in the last 30 days = **92.7 percent**.

| store | files | 30-day movement |
|---|---|---|
| vault | 285,960 | 0.3% |
| sessions | 942 | 92.7% |

Two stores with opposite behaviour, currently handled by one policy. So the deterministic rule he asks for does not need per-file prediction at all: the split is archive versus working set, and the two already sit in different directories.

That also answers his first question, "how many sessions exist and how often do files change in them", with a number rather than a plan: 942, and almost all of them, weekly.

### ⚠️ The ignore list is not the mechanism, by standing rule

`D:\OBSIDIAN\Anton-Knowledge\.stignore`, **14 lines**, carries its own warning dated 06.08.2026: only junk belongs here, entering real work is forbidden, because an ignore hides the file from view and the debt becomes invisible forever. Entries without `(?d)` are never deleted by Syncthing, merely not counted as changes.

So moving 200 thousand files out of sync via the ignore list would reproduce exactly the failure that rule exists to prevent. A second share with its own sync mode keeps the files visible and keeps them backed up.

⚠️ And a share nothing writes to is a share nobody notices breaking: whatever gets moved needs its own freshness check, or the archive becomes a silent single copy.

### Open, in order of payoff

1. Draw the boundary by directory, not by file type, since the type measurement says everything but markdown is already at zero.
2. Move the archive to a second share rather than into `.stignore`.
3. Give the new share a freshness and backup check before anything moves into it.
4. Re-measure after the split: the useful figure is bytes transferred per day, not file counts, and I did not measure bytes.
