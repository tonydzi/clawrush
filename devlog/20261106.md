**Class worth naming:** the dimension with a rule and a door drifts at 4 percent. The dimension with no rule drifts 267-fold. That is the whole argument for writing the methodology, and it is a measurement rather than an opinion.

### ⚠️ The ignore list is not the mechanism, by standing rule

`D:\OBSIDIAN\Anton-Knowledge\.stignore`, **14 lines**, carries its own warning dated 06.08.2026: only junk belongs here, entering real work is forbidden, because an ignore hides the file from view and the debt becomes invisible forever. Entries without `(?d)` are never deleted by Syncthing, merely not counted as changes.

So moving 200 thousand files out of sync via the ignore list would reproduce exactly the failure that rule exists to prevent. A second share with its own sync mode keeps the files visible and keeps them backed up.

⚠️ And a share nothing writes to is a share nobody notices breaking: whatever gets moved needs its own freshness check, or the archive becomes a silent single copy.

### Open, in order of payoff

1. Draw the boundary by directory, not by file type, since the type measurement says everything but markdown is already at zero.
2. Move the archive to a second share rather than into `.stignore`.
3. Give the new share a freshness and backup check before anything moves into it.
4. Re-measure after the split: the useful figure is bytes transferred per day, not file counts, and I did not measure bytes.

### ⭐⭐ Source №1 is the coding agent itself, and it has no off switch

Diagnosed 24 July 2026 and recorded in memory `black-windows-root-claude-code`: on Windows, Claude Code opens a visible console window for **every shell tool call**, and MCP servers launched via `cmd /c npx` add more. Proof was a comparison, not a guess: idle session, roughly zero windows; working session, one window per command. Checked against the docs by the claude-code-guide agent the same day: there is no setting, env var or flag to suppress them.

Which produces an uncomfortable property of this exact problem: while a session is busy diagnosing the flashing, the session is the main source of the flashing.

Two false roots were eliminated empirically before that: HP Sure Click / HP Wolf (full reboot with services disabled did not stop the windows) and the ChatGPT desktop app's `powershell Get-CimInstance` monitoring (killing it did not help).

### ⭐⭐ Four sources, four different cures, all already written down

From `~/.claude/skills/windowless/SKILL.md`, v1.0.0, 10,752 bytes:

| № | source | evidence | cure |
|---|---|---|---|
| 1 | Claude Code itself | no windows when idle, windows when working | no official switch, hider only |
| 2 | scheduled tasks with `LogonType=Interactive` | Interactive + sub-hourly repetition | flip to `S4U`, window physically cannot appear |
| 3 | MCP watchdogs respawning dead daemons via `cmd` | watchdog log "port dead → restart" every N minutes | flip watchdog to S4U and fix the daemon |
| 4 | child console exe from a script without `CREATE_NO_WINDOW` | window title is the exe name, parent chain leads to the script | `creationflags=CREATE_NO_WINDOW` in the calling code |

Source №4 was measured on this very laptop on 10 August: **120 windows per minute**, every one an `ssh-keygen.exe`, chain `Regress Grid Nightly` → `regress_run.py` → `fleet_sign.py` → ssh-keygen.

The hierarchy matters: S4U is the real fix because no window is ever created; the hider is a prop that hides what was already shown, so a one-frame flicker remains possible. The skill says so in its own text.

### ⭐⭐ Two fixes, opposite survival rates, and that is the rule

Measured on this node today, 56 active non-Microsoft tasks:

| property | count |
|---|---|
| `S4U` | **43** |
| `Interactive` | 11 |
| Interactive AND firing more than once an hour | **1** |

The one frequent flasher is named: `Claude Fleet Pulse Collect`, `PT5M`, running `python.exe fleet_pulse.py --collect`, last result `0x0`. That is 12 flashes an hour from the scheduler, and it is the only one.

So the S4U flip from 6 July survived four months untouched, while the hider from 6 August died after 37 days. The difference is structural: the flip changes a **property of the object** and needs nobody to keep it alive, whereas the hider is a **process** that has to keep running. A property-fix survives by default; a process-fix decays silently and therefore needs a watchdog over its own output age.

### ⚠️ Window composition differs per node, so the hub must be measured on the hub

Here: `ConsoleWindowClass` is 0.9 percent. On HP17 in late August the same class was **99.9 percent** of 54,032 events, and the cause there was a different one entirely: MCP watchdogs respawning `mongodb-sandbox` (8766) and `n8n` (8767), neither of which was actually in use.

Same symptom, same class of fix, completely different culprit distribution. Carrying this node's numbers over to the hub would be a guess wearing a measurement's clothes.

### 🤔 One hypothesis about the hub I cannot verify from here

The hub's Python 3.12 stdlib was destroyed on 2 October (memory `hub-python312-stdlib-destroyed-20261002`): all `.py` files gone, native binaries intact, every python routine on that machine red, cause never established, repair still waiting on Anton.

Source №3 is watchdogs that see a dead port and respawn the daemon through `cmd`. A dead interpreter means the respawn cannot succeed, so the watchdog tries again next tick, and every attempt is a window. The timing lines up with the complaint.

This is a hypothesis, not a finding. The evidence that would settle it is a watchdog log line on the hub, and the hub is not this machine. Worth noting that the audit script is PowerShell, not Python, so it would still run there.

### Open, in order of payoff

1. Run the audit on the hub: `windowless_audit.ps1` gives flashes/hour, hider state, MCP port state and which watchdogs are flapping. PowerShell, so the dead Python does not block it.
2. Restart the hider and put back its autostart, on whichever node is being fixed.
3. Give the hider's log an output-freshness watchdog. Everything above was discoverable from the log; nothing was watching it.
4. Decide whether `Claude Fleet Pulse Collect` is legitimately Interactive or should be flipped.
5. Only then consider new logging, if the existing log turns out to miss something.
