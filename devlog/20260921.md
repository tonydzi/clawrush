## LLM conversation harvest must run on every node

**Goal:** every deep research report, artifact and conversation from every LLM account lands in the vault, from every machine in the fleet.

**Constraint:** logins are per machine and per browser. Each node is signed into a different subset of ChatGPT, Claude AI, Mistral, Gemini and Grok, some in Chrome and some in Firefox. No single node holds every login.

**Consequence:** a single central harvester structurally misses whatever is only logged in elsewhere. The harvest is a routine on every node, not a job on one hub.

**Per-node routine, minimal form:**
1. enumerate browser profiles on the node (Chrome, Firefox) and the LLM accounts logged into each;
2. for each account, export conversations, artifacts and project or subproject contents;
3. write into the vault with provenance: node, browser, account, vendor, export time;
4. deduplicate across nodes by vendor conversation id, since the same account can be logged in on more than one machine;
5. report per node which accounts were harvested and which were found logged out.

**Invariant:** never assume one machine has all the logins. Collect where the login lives, and report the gaps instead of treating silence as "nothing there".

## GitHub contribution routines: expertise allow-list

**Goal:** every GitHub-facing routine on the Mac 16 laptop contributes only inside the owner's current areas of work.

**Allowed domains (from the post):** second brain (indexing, reindexing, embeddings, vector search, file administration), fleets of machines and agents, consensus between machines, outreach and leads, CRM, retros, compaction, routine improvement. The industry vertical of the target repository (crypto, medicine or anything else) is not a filter.

**Audit, minimal form:**
1. list every GitHub routine on the node and the search queries each one runs;
2. map each query to an allowed domain; a query with no mapping is out of scope;
3. check recent touches (comments, reviews, PRs) against the same map and count out-of-scope ones;
4. remove or rewrite out-of-scope queries.

**Invariant:** a contribution routine never acts outside the allow-list. When it detects a promising niche outside the list, it records a proposal for the owner and does not post there.

## Token cost per model and effort level: planned measurement

**Question:** actual token spend of Fable on low, medium and high effort; Opus on low, medium and high; Sonnet on medium and high. How much cheaper is low effort than medium or high for the same work?

**Why a price table is not enough:** per-token prices are fixed, but the number of tokens a task consumes depends on effort, because higher effort spends more tokens on thinking before answering.

**Method, minimal form:**
1. a fixed set of real tasks from daily work (short text edit, code fix, summarisation, planning), identical prompts;
2. run each task on every model and effort combination listed above;
3. record input tokens, output tokens (thinking included) and wall time per run, several runs each;
4. score result quality per task, so a cheap run that fails the task counts as a failure, not a saving;
5. publish tokens per task and cost per successful task for each combination.

**Measurement caveat already known on our side:** in session transcripts `output_tokens` covers the whole message (thinking, tool calls and text) and repeats on every record of one message id. Counting it naively inflates totals; deduplicate by message id first.

**Status:** planned as a deep research; no results yet.

## Starting a session from a Telegram message

**Problem:** a new Claude session can be started from a desktop, not from a phone. Tasks that come up away from the desk wait.

**Wanted:** a Telegram chat or group where the owner writes a task; a watcher (n8n or cron) sees each new message and starts a new session for it right away.

**Minimal design:**
1. one dedicated chat, messages accepted only from the owner's accounts;
2. a watcher reads new messages and records each as a task with the message id, so one message never starts two sessions;
3. the session starts with the message text as its brief and is visible in the app's session list, never a hidden background run;
4. the watcher replies in the same chat with the session name, or with the reason it did not start;
5. anything irreversible inside the session still stops for a human.

**Related mechanism already in place:** voice messages in the owner's archive chat already get one session each; this extends the same idea to typed tasks from the phone.
