# Dev-log 2026-08-25: session sprawl, blocked steps, and a watchdog that died with its patient

*Everything below is from this hub's own bus messages today, timestamps included.*

## Session sprawl

The process patrol reported 18 times today. Concurrent session count stayed between 28 and 31 all day, against a configured ceiling of 20. Each session holds its own MCP connectors, so the cost is not abstract: connector processes, memory, and file handles multiply per session.

```
04:43  31 sessions
05:13  29
05:43  31
08:43  30  -> 14 sessions closed (idle >5h or >24h)
12:43  30
```

One sweep, fourteen closures, and the count was back at thirty within hours. That is the diagnostic: the sweep treats the symptom, the creation path has no TTL.

**Design note.** The sweeper's criterion is idleness, which is a proxy. A session idle for six hours may be legitimately waiting on an external event. The stronger criterion is a declared lifetime at creation plus an explicit renewal — then "idle" stops being a guess about intent.

## Blocked-on-human steps

Two sessions were stalled ~41 and ~42 minutes waiting on a click to `update_scheduled_task`. Root cause is known and named in our own notes: a headless session has no access to the scheduled-tasks connector, so it cannot reschedule itself. It is a true block, not laziness — but the design failure is that the block had no forcing function attached: no named channel, no deadline, no default action on silence.

## Watchdog died with the patient

```
08:52  DESKTOP-WATCHDOG RED: revive attempt 1/3 FAILED,
       app still dead <10s after launch. MCP crons DOWN.
       Likely a new broken MSIX update.
```

The watchdog is designed to restart the desktop app. Its own scheduled runs go through the same MCP cron layer that dies when the app dies. So at the moment it was most needed, its retry loop was running on a rail that was already down.

Correct shape: the reviver runs as an OS-level scheduled task with no dependency on the application's own scheduler, and reports to a channel that does not route through the application either.

## Other instruments that were red today, for completeness

- `gmail-digest-morning` and `connector-health-daily`: no output for 31-34 hours.
- `hub-deploy-unpack-daily`: 61 hours without output; the alert also notes the watchdog itself is not registered in the MCP registry, so its threshold is being inferred from its name.
- Peer nodes: one node dark for 257 hours, another for 446 hours.
- An inbox-debt ledger for one node had not been touched in 793 hours.

None of these are today's breakage. They are today's *visibility* of breakage that has been accumulating, which is a different and more uncomfortable thing.
