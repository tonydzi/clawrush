### ⭐⭐⭐⭐⭐ (e) Cache hypothesis: confirmed, priced, and the window is 5 min / 1 h

**Live measurement, this session's own SessionStart hook:**

| field | value |
|---|---|

**Vendor documentation:**

| vendor | default retention | extended | write cost | read cost |
|---|---|---|---|---|
| Anthropic | **5 min** TTL, refreshed on each access | **1 h** via `cache_control: {ttl: "1h"}` | 1.25x base input (5 min), **2x** (1 h) | **0.1x** base input |
| OpenAI | **5-10 min** inactivity, **1 h** max (older models); **30 min** exact TTL on newer via `prompt_cache_options.ttl` | model-dependent `prompt_cache_retention`, 24 h on some | 1.25x uncached input on GPT-5.6+ | discounted 50-90% depending on model |

Sources: Anthropic prompt-caching docs; OpenAI prompt-caching guide; Bedrock/Vertex partner docs for the 1-hour TTL availability matrix.

**Verdict on the stated hypothesis:** mechanism correct, including "held in vendor RAM" - OpenAI's docs state cached prefixes live only in GPU memory. The stated window (40 min - 1 h) is long: real default is 5 min (Anthropic) or 5-10 min of inactivity (OpenAI); 1 h exists but must be requested and doubles the write price. The economic claim is right and larger than implied: a cache read is **0.1x** input, so continuing a warm session is an order of magnitude cheaper than restarting a cold one.

⚠️ Sources disagree on which retention tier applies to which model, and the figures are documented for API callers; a subscription seat is not guaranteed the same knobs. Direction certain, exact per-seat number not.

### ⭐⭐⭐⭐ (f) Tool survey: the industry's answer is for a different shape of system

Checked live. ## Post 4: cache TTL is 5 min not 1 h, the stale penalty is 12.5x not 2x, and this session's log shows 4.26B tokens read from cache

Source: Anton's post of 20 November 2026, 18:15 UTC. Claim under test: "in Claude Code, continuing a session an hour after the last message costs double; Codex sessions survive up to a day; Antigravity is opaque." He explicitly asked to be corrected. Measured on MyOwnPC-Natalia and in this session's own transcript.

### ⭐⭐⭐⭐⭐ (a) The window: 5 minutes, and the change is recent and Claude-Code-specific

| fact | value |
|---|---|
| Anthropic default cache TTL | **5 minutes** |
| optional TTL | 1 hour, on request |
| 5-min cache **write** | 1.25x base input |
| 1-hour cache **write** | **2x** base input |
| cache **read** | **0.1x** base input |
| lifetime behaviour | refreshed on every access |

The Register reported Anthropic **cut the Claude Code prompt cache TTL from 1 hour to 5 minutes** for many requests, stating it should not raise costs; a third-party developer analysis estimated **+20-32%** in cache-creation cost from the shorter TTL. ⚠️ Dates in the secondary coverage disagree (February / March / April 2026); the direction is consistent across sources.

**Verdict on his claim:** the "one hour" rule was correct until this spring and is now wrong by a factor of 12. His error is in the *comfortable* direction - he believes caches are warm that are already cold.

### ⭐⭐⭐⭐⭐ (b) The lever exists and is unset here

`CLAUDE_CODE_PROMPT_CACHE_TTL` accepts `5m` or `1h`.

```
~/.claude/settings.json          env keys = 8, cache-related: NONE
~/.claude/settings.local.json    env keys = 0, cache-related: NONE
project .claude/settings*.json   absent
process environment              CLAUDE_CODE_PROMPT_CACHE_TTL = (unset)
```

Every session on this node therefore runs the 5-minute default. Buying the hour costs 2x on writes - which is the origin of his "double price", misattributed: **2x is the price of extending the cache, not the penalty for losing it.**

### ⭐⭐⭐⭐⭐ (c) The real stale-cache penalty is 12.5x, computed at Opus list prices

Opus input $15/M:

| operation | multiplier | $/M | vs a warm read |
|---|---|---|---|
| warm read | 0.1x | $1.50 | 1x |
| write, 5-min TTL | 1.25x | $18.75 | **12.5x** |
| write, 1-hour TTL | 2x | $30.00 | **20x** |

His "double" understates the penalty by an order of magnitude. ### ⭐⭐⭐⭐ (f) Codex: his claim is correct and documented

OpenAI `prompt_cache_retention`:

| policy | lifetime |
|---|---|
| in-memory | 5-10 min of inactivity, **max 1 hour** |
| extended | **up to 24 hours** |

Newest models: 30-minute minimum by default, 12-hour option via `prompt_cache_options.ttl`; the vendor may retain longer than requested. ⚠️ A community report claims the GPT-5 series defaulted to 24-hour retention from 29 May 2026 for orgs without Zero Data Retention - unconfirmed against OpenAI docs.

**Verdict:** "supposedly their sessions do not expire for up to a day" is right. Net result for the post: he was wrong about his primary vendor and right about his secondary one.

### ⭐⭐⭐⭐ (g) Antigravity opacity has a cause

Google moved metering from prompt counts to a **compute-used** model, with purchasable extra Antigravity credits. There is no cache TTL to discover because the billed unit is not a request or a cached prefix. Not a knowledge gap on his side - a different billing model.

### Open, in order of payoff (post 4)

1. **Decide the TTL deliberately.** `5m` default vs `1h` at 2x writes is a one-line env var, currently unset. For a workflow with long human pauses the hour may pay for itself; nobody has priced it.
2. **Add the missing vendors to the ledger.** Cursor, Kimi, OpenRouter, the Antigravity seats, prices for GLM and Mistral. The $540 headline is wrong low, which is the worst direction for a budget number.
3. **Surface the cold-start count, not just the cost.** The harness prints `estimated_cache_write_usd` per resume; nothing aggregates it. 108 cold starts in this session is the number that would change behaviour.
4. **Treat compaction as a cache decision.** 4.26B read vs 62.7M written means the cache is doing the work; a compaction that shrinks the prefix also shrinks every future warm read.
