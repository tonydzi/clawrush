### ⭐⭐⭐⭐⭐ (e) Cache hypothesis: confirmed, priced, and the window is 5 min / 1 h

**Live measurement, this session's own SessionStart hook:**

| field | value |
|---|---|
| `seconds_since_last_response` | **247,094** (68.6 h) |
| `prompt_cache_likely_expired` | **true** |
| `estimated_cache_write_usd` | **$9.2763** |
| `context_tokens` | 927,627 |

**Vendor documentation:**

| vendor | default retention | extended | write cost | read cost |
|---|---|---|---|---|
| Anthropic | **5 min** TTL, refreshed on each access | **1 h** via `cache_control: {ttl: "1h"}` | 1.25x base input (5 min), **2x** (1 h) | **0.1x** base input |
| OpenAI | **5-10 min** inactivity, **1 h** max (older models); **30 min** exact TTL on newer via `prompt_cache_options.ttl` | model-dependent `prompt_cache_retention`, 24 h on some | 1.25x uncached input on GPT-5.6+ | discounted 50-90% depending on model |

Sources: Anthropic prompt-caching docs; OpenAI prompt-caching guide; Bedrock/Vertex partner docs for the 1-hour TTL availability matrix.

**Verdict on the stated hypothesis:** mechanism correct, including "held in vendor RAM" - OpenAI's docs state cached prefixes live only in GPU memory. The stated window (40 min - 1 h) is long: real default is 5 min (Anthropic) or 5-10 min of inactivity (OpenAI); 1 h exists but must be requested and doubles the write price. The economic claim is right and larger than implied: a cache read is **0.1x** input, so continuing a warm session is an order of magnitude cheaper than restarting a cold one.

⚠️ Sources disagree on which retention tier applies to which model, and the figures are documented for API callers; a subscription seat is not guaranteed the same knobs. Direction certain, exact per-seat number not.

### ⭐⭐⭐⭐ 🤔 (f) The n8n takeover may be canon, not improvisation

Hypothesis, unconfirmed - the incident happened on his machine; measurements here are from this node.

Canon carries a standing rule that **every voice memo raises its own session**, with a dedicated skill as its door. An LLM carrying a voice memo from Telegram into a harness and raising a session is therefore a documented behaviour, not necessarily an invention. If the n8n converter was mid-migration between machines, the expensive path was the only one left.

Consequence if true: the defect is not a rogue agent but **a rule with no cost ceiling** - "always raise a session" and "a session may re-read ~1M tokens of context" were specified independently and never priced together.

Not asserted. What is measured here: zero rogue continuations found in this node's audit, and 123.3M tokens of legitimate, scheduled background burn in one day.

### Open, in order of payoff

1. **Read the three unread vendor panels.** $540/month is being spent against three "not measured" rows. This is the only item that needs no code - just a login and a number written down.
2. **Un-stick or disable the 21 tasks.** They are enabled and overdue 100 days; either the folders come to this node or the entries get disabled with a reason. Leaving them enabled makes the registry lie.
3. **Put a cost ceiling on the per-run background routines.** 31.5M tokens in one teaser run is a measured, repeatable, by-design spend. A per-run token budget with a hard stop is a smaller change than re-architecting the routines.
4. **Prefer warm continuation deliberately.** A cache read costs 0.1x; a cold resume of this session cost $9.28. Where a routine wakes an old session, waking a fresh short one may be cheaper than resuming a megabyte-sized old one.
5. **Compact or split the top re-read session.** The audit flags it by name every day it exceeds the threshold; today it was 6,905.7M re-read over 11,649 turns.
