## Routine self-repair and the inheritance problem

**Observed:** routines rewrite their own instruction after a failed attempt, so the next attempt of the SAME task is better.

**Open question:** does a later run inherit that rewrite? A scheduled run starts with no memory of prior runs. The only channel between runs is persistent state: the instruction file, a progress journal, and whatever the run chooses to write down.

Two designs, and their costs:

| design | how the fix survives | cost |
|---|---|---|
| rewrite the instruction | fix becomes part of the prompt every future run reads | instruction grows; needs pruning or it turns into the always-loaded bloat problem |
| carry recent history | next run reads the last 3-5 run logs | context cost scales with history length; the lesson is buried in noise |

**Preferred invariant:** a fix from any of the last N runs must be present in the instruction in a form a zero-context reader acts on. History is evidence, the instruction is the contract.

**Known failure mode from our own fleet:** a routine fixed its OWN file and reported "updated", while the real canonical door, a shared skill, kept the opposite rule. Fixing the local copy while the shared source stays wrong is half a fix. Rule adopted 13.09: every routine that did useful work issues two verdicts in the same run, one for the skill it used and one for its own instruction.

**Related trap:** the progress journal must never live in a synced folder. Measured 23.08: a routine chewed the same chunks for 19 days, because sync overwrote its journal before the next run read it.
