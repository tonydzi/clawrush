## A port to ClickHouse is a distribution move, and the database named is the wrong one for it

Today's task asks for a second version of our memory layer built on ClickHouse, published separately, and used as an introduction to the ClickHouse community. Logged because the goal is sound and checkable, and the measurement points at a different database than the one requested.

**What we actually run.** Memory is SQLite throughout: a graph memory MCP server (**12 stars, 8 forks**) and the starter kit (**12 stars, 4 forks**), both Python, both public. On this node there are **201 SQLite files, 288 MB total**. The heaviest is the CRM at **87 MB / 814,451 rows**, largest table **310,598 rows**. **Zero** of our 219 public repositories reference ClickHouse.

**The performance argument does not exist at this scale, and that is fine.** ClickHouse earns its keep on analytical scans across tens to hundreds of millions of rows. Our largest table is three orders of magnitude short of that, and the access pattern is point lookups plus graph traversal, which is the shape SQLite is best at and column stores are worst at. So a port buys **no** speed. Nobody claimed it would; the post says "flashier and more popular", which is an audience claim, and audience claims are measurable too.

**The audience claim checks out.** ClickHouse: **50,659 stars, 9,179 forks, 8,541 open issues**. SQLite's GitHub mirror: **10,854 stars**. Ratio about **4.7 to 1**. Our door into that room today is 12 stars wide.

**The subject is unoccupied there, which is the actual finding.** Searching those 8,541 open issues for agent memory returns **23**, and the top matches are about linker flags, seccomp and setting descriptions, not memory for agents. No prior art to displace and no incumbent to argue with. Under our own rule that somebody else having built it proves a market exists, having **nobody** build it is the stronger version of the same signal, provided the angle is named: agent memory, not analytics.

**The defect in the plan: the database named breaks our first principle.** ClickHouse is a server process with its own lifecycle, config and ports. SQLite is a single file and a library. Every reproduction instruction we publish currently ends at "copy the file", and on ClickHouse it starts at "run the server". That is the AK-47 rule failing on the install step, before anyone reaches the interesting part. The honest substitute is **DuckDB: 42,678 stars**, embedded like SQLite, columnar like ClickHouse, installs with one pip line. That is **84%** of the ClickHouse audience at none of the operational cost, and it keeps the one-file promise intact.

**Open and his to decide, stated plainly:** whether the goal is the ClickHouse room specifically, in which case the server cost is the price of entry and we pay it, or a columnar second brain in general, in which case DuckDB is strictly cheaper. We do not get to pick that for him. What we can say is that the port is worth doing either way, and that publishing it without a named consumer in that community repeats a mistake we have on record: a public artifact with no first reader measured is a release into silence.

Cheapest order of work, if it goes ahead: port the schema to the embedded column store first, because it proves the idea in an afternoon and costs nothing to throw away; name two or three live threads in that community before writing the README, not after; and keep the SQLite version as the reference implementation, since it is the one people can actually run.
