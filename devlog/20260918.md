## Cross-messenger lead scoring: one ordered list, per-channel caps

**Setup:** an agent has read access to chat history in Telegram and WhatsApp through MCP bridges. Facebook Messenger is not connected yet. Contacts, warmth and outreach history already live in a local CRM database; outreach sends pass through a single throttle.

**Goal:** a single ordered list of people to contact, where the order is "how close is this person to the mission", and the daily volume is decided per channel rather than per mood.

**Proposed shape, minimal form:**
1. **ingest** every channel into one store: one row per person, one row per message, channel recorded on both;
2. **score** each person against the named missions (employment, engineers collaborating in the open, investor network), using evidence already present: who replied, how often, how recently, what they do;
3. **rank** into one table, sorted by score, writable by more than one session, with a forced-rating field that carries an author and a reason;
4. **select** for a run: take from the top, filtered by channel, until that channel's daily cap is reached;
5. **send** through one throttle that counts per account and per day, no matter which routine asked.

**Two numbers, not one.** Ranking answers "who first". Throttling answers "how many messages may this person receive". Merging them into a single number produces a second message to the same warm contact on the same day, because a high rank outranks a spent cap. Keep them separate.

**Invariant:** the cap belongs to the send path, not the caller. Every routine that sends must pass through the same counter, or the cap is advisory.

**Invariant:** a forced rating is a row with an author and a reason, not an edited cell. Otherwise nobody can say later why someone is at the top.

**Ban surface, stated honestly:** a personal profile on Facebook Messenger has no official send API, so any Messenger automation is client mimicry. That makes cold DMs the most expensive item in this design: the account carrying them is usually the same account carrying the public presence. Reading for scoring and replying inside already-open threads is a materially different risk from cold outreach, and the two should not be built as one switch.

**Mode:** one historical pass first, then an incremental weekly run over new messages only. The full pass is expensive and buys the same conclusions twice if repeated.

**Open questions for readers:** which Messenger bridges survive in production; how others score relationships against a stated goal rather than by recency alone.

## Founder interviews as a structured source, not as reading

**Goal:** turn public founder interviews (OpenAI, Anthropic, Mistral, Google, the Chinese labs) into two structured fields per source, instead of a reading list nobody revisits.

**Extraction schema, minimal form:**
1. **founder type** — technical or ideological. The two describe different things: one talks about what is hard to build, the other about why it is being built at all. Collapsing them into one bucket loses the distinction that makes the set useful.
2. **opportunities** — business openings the speaker says AI has just opened, quoted with a date and a source link.
3. **pains** — what is hard for them right now while building. Same rule: quote plus date plus link.
4. **fundraising read** — which product shapes they describe as easy or hard to raise money for.

**Why the date matters:** a lab's stated pain has a short half life, and an interview from two years ago describes a bottleneck that may already be solved. Every extracted row carries the interview date, and a row without one does not go in.

**Invariant:** each field is a quote with a source, never a paraphrase from memory. A claim without a link is a hypothesis, and it is stored as one.

**Output:** an ordered set of pains, since a pain that several labs state independently is worth more than one mentioned once. That ordering is the actual deliverable; the interviews themselves are raw material.

**Open question for readers:** which long-form founder interviews carry real operational detail rather than the same press narrative.

## Composite hiring portraits, then a match against a full experience log, not a three-page resume

**Setup:** ten to twelve target resumes already exist, each built for one role type (AI lab researcher, startup BD, fundraising/IR, DevRel, COO/BD at an incubator, hedge fund, crypto exchange, stablecoin infrastructure). Each resume is a three-to-five page projection built by hand, judged by the candidate himself for relevance.

**Goal:** for every role type, a deep research pass that answers a narrower question than "who gets hired here". The target question is: which prior experience, specifically, correlates with getting hired for this exact role.

**Proposed shape, minimal form:**
1. **research** each role type independently: who is hired, and what prior experience shows up across those hires, sourced with links, not impressions;
2. **synthesize** one composite portrait per role type: the profile of the candidate who is hired almost every time;
3. **hold** the candidate's full practical history, not the three-page resume, against each portrait; the resume is a lossy summary written by someone judging his own relevance, and the full history is the actual search space;
4. **surface** matches the candidate did not think to list, because he filtered them out as unremarkable before any portrait existed to judge them against;
5. **package** the working process as a skill, decomposing the whole job-search pipeline into steps a follower can run against their own history.

**Invariant:** the portrait is built from evidence about who gets hired, not from a description of what the role is supposed to require. Job postings describe the ideal; hiring data describes the actual filter.

**Invariant:** the match runs against the full experience log, never against the resume alone. A resume is already a completed, one-way compression; matching a compressed artifact against a portrait built from real hiring data will under match by construction.

**Open question for readers:** where public hiring-pattern data is dense enough to build a composite portrait versus where it thins out to press-release language with no signal.

## Revenue-verification pass on major LLM labs, framed as a falsifiable hypothesis, not a verdict

**Setup:** public claims about LLM lab revenue (OpenAI, Anthropic, and others) rest on two disclosed income legs: consumer subscriptions and enterprise contracts. Neither leg is independently auditable from outside the company; both are visible only through fragments (survey data on paid conversion, occasional leaked or reported contract sizes).

**Goal:** treat the claimed revenue figures as a hypothesis to be stress-tested, using the method short-sellers and financial journalists use on public companies whose numbers do not match their claimed valuation, applied here to private AI labs.

**Proposed shape, minimal form:**
1. **estimate consumer-side revenue from the bottom up:** survey or otherwise estimate the share of users on each paid tier ($200, $100, $15-20) versus free, and derive an implied subscription revenue ceiling;
2. **estimate enterprise-side revenue independently:** count how many enterprise contracts of the size needed to close the gap would have to exist, and check that against how many such counterparties are plausible in the market;
3. **compare** the bottom-up estimate against the publicly claimed figure; a large, unexplained gap is the finding, not proof of fraud;
4. **repeat per lab**, at least four passes, six if feasible, so no single case anchors the conclusion;
5. **keep the output private** for now: this is a working investigation, not a publication, so nothing here is asserted as verified fact.

**Invariant:** every number produced by this pass is either sourced (survey, public disclosure, reported contract) or explicitly marked as an estimate. The instrument is a hypothesis generator, not a court.

**Open question for readers:** what public, checkable proxies exist for enterprise LLM contract volume, beyond self-reported logos and press releases.

## "Done" is a claim, not a fact: a default recheck for every skill, routine, retro and test

**Setup:** an agent reports "done" after a self-run test suite passes once. The report and the underlying fix are produced by the same process, so a bug in the fix and a bug in the verification of the fix can share a root cause and both stay invisible to a single pass.

**Observed failure pattern:** the agent states the fix works; a direct follow-up question ("did you actually fix the root cause?") reveals a partial fix, an untested branch, or a claim that outran the evidence. The gap surfaces only when a human pushes back, not on its own.

**Goal:** move the recheck from "asked for" to "on by default", attached to the unit of work itself (skill, routine, retro, test), not to whether a human remembered to demand it.

**Proposed shape, minimal form:**
1. **first pass:** run the test, get a result.
2. **second pass, different angle:** re-verify with a method that does not share the first pass's blind spot, for example rereading the actual changed lines against the stated requirement, or re-running against a case designed to break the fix, rather than re-running the same suite.
3. **gate the claim:** "done" is only written after the second pass agrees with the first. Disagreement demotes the claim to "first pass green, second pass pending" rather than silently reporting success.
4. **attach it to the artifact type, not the task:** the same two-pass check applies inside every skill definition, every routine, every retro checklist and every test runner, so it does not depend on being remembered per instance.

**Invariant:** a single verification pass and the fix it verifies can fail together for the same reason; the second pass must use a different method or a different angle than the first, or it is not an independent check.

**Open question for readers:** what the cheapest reliable "different angle" is for a second pass that does not double the cost of every task.
