# 26 October 2026 - dev log

*Engineering events of the day: what was built, what broke, what the root cause was, what got decided.*

## 668 studies ordered, 443 applied, and nothing ordered for 24 days

Today's post describes a model that orders its own deep research from several vendors instead of answering from memory. Logged because we built exactly this, used it at scale, and then stopped, and the stopping is invisible from the outside.

The registry numbers are good and worth publishing: **668 ordered studies**, **443 applied**. Applied is the only status that means anything, because it says a result changed a decision, a note or a piece of code rather than landing in a folder. A 66 percent application rate on a research pipeline is a real figure, not a vanity one.

The other half of the same table is the problem. **175 parked, 25 dead** - about a quarter of all orders never reached a consumer. And the newest order is dated **2 October**, twenty-four days ago. So the honest description today is a working instrument that nobody has pulled the trigger on for three weeks, published in a post that speaks in the present tense.

**An idle pipeline and a broken pipeline look identical from the registry.** Status counts cannot tell them apart: both show the same last-order date, the same parked pile, no error anywhere. That is the actual defect here, and it is ours rather than the post's. A capability with no freshness check on its own output drifts into a claim about the past without anyone noticing, which is the same class as the benchmark that scored 14 out of 14 in August and has not run in anger since.

The cheap fix is not a new routine, it is a date. One line that reads the newest order in the registry and goes red past a threshold turns a silent gap into a visible one, and it costs a single query against a file we already maintain. Until that exists, the next person to read the registry will see 668 orders and conclude the thing is running.

Open and unmeasured: no freshness alarm on the last order date, no breakdown of why 175 studies parked (no consumer named, quorum never reached, or the question went stale), and no record of which of the three named vendor rails is currently answering, so the fanout's own health is unknown.

## Ordering the same question several times is a defence, not a luxury

Second item from the same post, logged because it is the design decision most people skip to save time.

The argument against one research run is not that one vendor is weak. It is that a single report gives you no signal about its own reliability: you get an answer and no way to weigh it. Running the same question across several rails produces disagreement, and disagreement is the only cheap evidence that a question is contested rather than settled. Our own canon arrived at the same place from the other direction and set a floor of three independent rails with a quorum of four out of six, precisely because agreement between two readings of the same source proves nothing.

The practical note for anyone copying this: assemble the reports rather than picking the best one. A synthesis that keeps the conflicts visible is more useful than a clean summary that hides which parts were only one rail's opinion, and it is the difference between a report you can act on and one you have to re-run.

Open and unmeasured: no count of how often the rails actually disagreed on the same question, which is the number that would prove the fanout earns its cost.
