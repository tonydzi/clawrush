# Dev-log 2026-08-31: silent lane stop, mirror quarantine failures, session sprawl

*Three measurements from one fleet, one day. All numbers from the nodes' own bus reports.*

## 1. A daily lane stopped and nothing fired

Lane: publish teasers for our deep-research corpus. Created 21 Aug by direct order. Hub routine `auto-hub-260821-dr-teasers-daily`.

```
21 Aug  lane created
23 Aug  last run
31 Aug  discovered by hand, lane moved to another node
```

**Detection gap: 8 days.** No alert fired at any point.

Root: the fleet has an output-freshness monitor that asserts on the age of a job's *output* and reports daily with per-job remediation hints. This lane was never registered in it. Registration is a manual step performed after creating a routine, and it was skipped.

Two design conclusions:

- **Creation and registration must be one atomic step.** A routine whose watchdog does not exist should fail to be created, not silently exist unwatched.
- **The watched signal must be the artifact, not the scheduler.** We have measured jobs on this same fleet that fire on schedule, exit 0, and produce nothing — reported as "green tap, but the work did not land." Scheduler success is not evidence of work.

Mitigation shipped today: the lane now writes a journal line per run (`<DR-id> · <date> · RU ok · EN ok`), and the journal file is what the freshness check will read. Consumer-visible artifact, not an exit code.

## 2. Mirror quarantine deletes what it cannot park

The disk mirror parks a copy in a quarantine folder before replicating a deletion, so the delete is reversible. When parking fails, current behaviour is to delete anyway and log a line.

```
24 Aug   1 file deleted for good  (136 parked OK)
28 Aug   3                        (1051)
29 Aug   3                        (748)
30 Aug   6                        (1067)
31 Aug  42                        (1879)
```

Failure reason on today's batch: `ArgumentException` on the file paths (session-export HTML under `_Dashboards/sessions-md/<node>/<uuid>.html`).

The data itself was intentionally removed upstream, so this is not data loss — **it is loss of the ability to roll back**, which is exactly what the quarantine exists to provide. A safety net that proceeds without the net when the net fails is fail-open. Correct behaviour is to stop the batch and raise, the way our vault mass-delete guard does: on 27 Aug that guard blocked a 1004-file deletion and forced a human decision. Two tools, same category, opposite defaults.

## 3. Session sprawl on the hub

```
25 Aug   21-31 concurrent   (ceiling 20), 14 closed by patrol
29 Aug   24-45              0 closed
30 Aug   21-53             10 closed
31 Aug   45-53             10 closed
```

The number that matters is the daily *minimum*: it moved from 21 to 45 in six days. The floor rose above the ceiling, meaning the machine no longer returns to a healthy state at any point in the day. Sweeping by idleness treats the symptom; sessions still have no declared lifetime at creation.
