## A recorder that reported healthy while it recorded nothing, and a licence that stopped being open-source

Second post of the date. Request: find a ready open-source replacement for Screenpipe that runs on Mac and Windows, listens continuously to everything on the machine and writes audio only, no video; plus establish what people complain about, and whether the project is genuinely open-source or the parts you need are shut inside binaries. Logged because the licence answer invalidates the binaries premise, and because our own two incidents turn out to be an instance of a defect their tracker has carried since 2024.

**Licence, from the primary source rather than from guides.** `LICENSE.md` on `main` is headed **Screenpipe Commercial License**, copyright **Negentropy Labs, Inc. (dba Screenpipe)**. Section 4: commercial use "requires a paid Screenpipe Enterprise plan and a commercial license from the Licensor expressly covering that use." Section 3: the licence "governs the source code of the Licensed Work and any binaries built from it by you or by third parties", and "does not govern official prebuilt builds of Screenpipe distributed by the Licensor", those being under the Terms of Service. Carve-out: versions "previously released under the MIT license remain available under the MIT license." ⭐ So the premise of his fourth question is wrong in a useful direction: the code is readable and patchable, and the restriction is on *use of the result*, not on access to the parts. A fork maintained for internal commercial use is a licence question, not an engineering one. ⚠️ Search engines returned the copyright holder as "Mediar, Inc."; the file on `main` says Negentropy Labs, so the search snapshot was stale and the primary source corrected it.

**Context for the change.** Repository description and README heading read `screenpipe | YC S26`, repo tagged `ycombinator`; desktop plans Free / Basic / Business with Enterprise per deployment, new lifetime licences withdrawn and existing ones honoured. Third-party pages still describe the project as MIT-licensed, i.e. the public description and the LICENSE file disagree. ⚠️ Date of the change not established: a mirrored README carries "06/10" with no year and ambiguous ordering. Worth pinning down, because any binary built before that date stays MIT.

**Reported defects.** **#183** (Aug 2024): CPU >100%, memory >10GB, settings page reporting "healthy". **#278**: $300 bounty on a memory leak; target "24h under 6GB", reported 8GB/30min and 20GB/20h; issue author names ffmpeg and SQLite as suspects. **#7059** (~46 days): Windows-wide sluggishness and cursor lag during recording, CPU ~28%, ~1.6GB resident, **>300 threads**. **#1202**: `screenpipe pipe info` fails with a response-decoding error, the only "broken API" report found. README claims 5-10% CPU, which conflicts with the above and is presumably workload-dependent. ⚠️ Per-issue open/closed state unverified; some may be fixed in later releases.

**Our own two incidents, and why they are one class with #183.** 28.09: a Screenpipe update relocated its database; the watchdog continued reading the previous file, where nothing changes, and continued reporting healthy. Underneath, audio transcription had been stalled since 27.09 13:30 (>24h): a process hung on a read, the database could not flush, queue depth reached **60,000 pages**. Detected only because a call was missing from the recording at follow-up time; the transcript survived via Fireflies recording in parallel. Fix applied then: watchdog repointed at the new database path, plus two new signals (transcription lag, database queue depth), plus a test that reddens against the old watchdog. 30.09: the audio rail silent **5.4 days** while aggregate health still reported "active". ⭐ Both ours and #183 are the same defect shape: *the status surface is derived from something other than the artefact*. Our cure was to measure the age of the newest transcript; theirs is unfixed as far as the tracker shows.

**Replacement candidates, measured against the stated requirement (cross-platform, continuous, ambient, audio-only, open licence).** **Meetily** / `Zackriya-Solutions/meeting-minutes`: "MIT License - Feel free to use this project for your own purposes"; installers Windows `x64-setup.exe`, macOS `.dmg` (aarch64), Linux build-from-source; capture "microphone and system audio simultaneously with intelligent ducking and clipping prevention", no video; on-device Whisper or Parakeet; summaries offer Ollama (local) **or** Claude / Groq / OpenRouter, so cloud egress is a default to be closed. Gap: it is organised around meetings and makes **no always-on claim**. **Parrot**: macOS only. **whisper-stream**: bash + silence detection, not a daemon. **OpenRecall**: screenshots, no audio. **Microsoft Recall**: no audio.

**Measurement boundary.** Licence text, repo tagline and issue numbers are read from primary sources. Alternatives are from search results plus the Meetily repository page; none were installed or benchmarked here, and "no always-on ambient open-source daemon exists" is a *not-found*, not a proof of absence. Our incident details come from the hub's 28.09 retro and the 30.09 measurement; this node runs neither rail, so nothing about current Screenpipe state on the fleet was checked live from here.

**Open and unmeasured.** Does Meetily run continuously, or does it require a meeting to start: unchecked, and it decides the whole question. Date of the licence change: unknown. Whether the real requirement was ambient audio or call audio: unargued, and the 28.09 incident is evidence for calls, since Fireflies, a call recorder, is what saved it.

## An accurate counter wired to the wrong rule: 281 unpaid tasks and a hook that says take the oldest

Third post of the date. Request: establish how cross-machine updates should work, given that each machine currently pulls and applies by hand, the local routine cannot keep pace, and debts accumulate in the inbox; plus survey how others build update, queue and inbox mechanics, and how to keep the inbox from accruing debt. Logged because the measurement turned the question around: the counters are correct and the instruction derived from them is inverted.

**Measured here, this node, today.** Bus ledger: `total=425 paid=144 unpaid=281`, oldest unpaid around **1009.9h** (~42 days). Bus root resolved from `machine.env` as `MACHINE_BUS_DIR` (not from the vault, which holds a frozen twin). `_deploy` directory: **66** entries. Apply machinery present: `deploy_lib.py`, `deploy_apply.py`, `deploy_register.py` under `~/.claude/scripts`, `inbox_daily.py` under the project tools. So the pipeline exists end to end; the failure is in ordering and admission, not in the absence of an applier.

⭐ **The defect, and it is ours.** The session-start hook prints, for the accumulated debt, an instruction to take **the single oldest** item and close it in the same session. The task registry independently surfaces "longest without movement" as the thing to look at. Two instruments, same bias, both pointing at the oldest entry on a backlog that is 281 deep. AWS's "Avoiding insurmountable queue backlogs" states the opposite preference directly: *"Real time systems often are implemented with FIFO-ish queues, but prefer LIFO-ish behavior."* The oldest item is the one most likely to be stale or superseded, and spending the session on it is the mechanism by which the fresh item becomes the next stale one. This is not a counter that lies, which is the 28.09 class; it is a counter that is right attached to a rule that is wrong, and that survives review precisely because the number checks out.

**Named mechanisms available, from the same source.** Backpressure to producers by scaling the inbound throttle down as backlog grows; sidelining old traffic into a secondary queue drained after the live one; dropping messages a later full sync supersedes (TTL); dead-letter queues with an alarm, on the principle that anything landing there is a bug to investigate; capping in-flight messages instead of leaving them invisible-but-in-flight; heartbeating long work to extend visibility rather than risk redelivery and parallel double-processing; per-workload concurrency limits via separate pools and semaphores; spare polling capacity for bursts; per-producer fairness and shuffle sharding where many producers compete. Secondary sources add bounded retries with exponential backoff before the dead-letter hop, idempotent handlers because at-least-once guarantees duplicates, and alarming on dead-letter depth. One of them states the general case usefully: a queue does not remove overload, it delays the moment overload becomes visible, which is a precise description of a 281-item inbox that nobody experienced as an incident.

**Distribution side, surveyed against the stated requirement (Windows and Mac, per-platform paths, install-time steps, converge without being told).** **chezmoi**: covers Windows, macOS, Linux; git repo plus templating for per-machine divergence; own docs position it below full configuration management. **Nix** + nix-darwin + Home Manager: declarative and reproducible, **no Windows**. **Ansible**: the usual pick when Windows is in the fleet, repeatedly described as better at push than pull, which is the opposite of the self-converging behaviour wanted here. **Fleet** + osquery: device management and compliance. ⚠️ No single declarative pull-model tool covering all three platforms was found; the recurring community pattern is two tools split by platform. That is a not-found rather than a proof of absence.

**Mapping his own simple-versus-complex split onto the mechanisms, since it is the right axis.** Simple updates (file arrives, lands in the working folder, done) are idempotent drops, which makes them both safe to expire under a TTL and safe to replay; most of the backlog is presumably this class. Complex updates (platform branches, path rewriting, install-time steps) are the ones that can fail unapplyably, and therefore the ones that belong in a dead-letter lane with the reason captured, rather than in an unbounded retry against a live queue.

**Measurement boundary.** All counts are from **this node** (MyOwnPC-Natalia): bus ledger, `_deploy` listing, local script presence. Other nodes may carry different debt and a different applier state, and the hub holds the authoritative parcel registry. Nothing was changed: no TTL set, no parcel expired, no hook edited. The AWS mechanism list is read from the article itself; the PDF mirror did not parse, so the HTML version at `builder.aws.com` was used after a 301 from the old `aws.amazon.com/builders-library` path.

**Open and unmeasured.** Composition of the 281: how many are supersedable file drops versus real pending work, which decides whether TTL alone resolves it. Whether the oldest-first instruction is hard-coded in the hook or configurable. Whether parcels already carry a timestamp usable as a TTL input without schema change. And whether per-node debt differs enough that the backlog is really one queue or several.
