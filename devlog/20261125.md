## Post 2, correction issued 2026-11-26: the published timings were a single cold run and overstate the per-edit gate by 4.5x; the real distribution is 79% in the Bash chain

**Why this correction.** Section (e) above reported one cold run per hook. Re-measured with **n=7 runs per hook, median reported**, on the same node, same payloads:

| metric | cold single run (published) | median of 7 | delta |
|---|---|---|---|
| `receiveonly_edit_guard` | 1.93 s | **0.43 s** | overstated 4.5x |
| `Write`/`Edit` chain (4 hooks) | 2.32 s | **0.87 s** | overstated 2.7x |
| `Bash`/`PowerShell` chain (8 hooks) | 0.81 s | **1.04 s** | understated |
| weekly total, this node | "≈6.8 h" | **5.74 h** | close, wrong decomposition |

Per-hook medians, Bash chain: `blackbox_session_guard` 0.203 · `av_spawn_guard` 0.171 · `onair_fleet_guard` 0.127 · `public_tg_shell_gate` 0.124 · `block_dangerous_bash` 0.112 · `maintenance_gate` 0.110 · `radical_order_gate` 0.098 · `dr_start_guard` 0.092. Write chain: `receiveonly_edit_guard` 0.430 · `constitution_guard` 0.173 · `memory_write_gate` 0.153 · `onair_fleet_guard` 0.115.

**Weekly split, corrected.** 15,581 shell calls × 1.04 s = **4.50 h (79%)**; 5,117 edits × 0.87 s = **1.24 h (21%)**. The earlier claim that the per-edit gate dominates was wrong: the shell chain dominates, because it fires three times as often.

**The stated cause was also wrong.** Measured in-process, not by subprocess wall clock: `api_key()` **0.001 s** · `rest("/rest/config/folders")` **0.005 s** (9.8 KB response, 7 folders) · `rest("/rest/db/file")` **0.163 s** · `decide()` end to end **0.006-0.009 s** on all three reference paths. The REST call is not the cost. Process startup is: bare interpreter **0.062 s**, `import urllib.request` **0.148 s**, `import xml.etree.ElementTree` **0.051 s**. ⚠️ The published line "the gate makes two REST calls" is also only true for receive-only folders - for `sendreceive` folders and paths outside any folder, `decide()` returns before the `/rest/db/file` lookup, so the common case made exactly one call.

**Fix applied in this session** (`~/.claude/hooks/receiveonly_edit_guard.py`, backup at `hooks/_backups/receiveonly_edit_guard.py.before-cache-20261126`):
1. `urllib.error`/`urllib.parse`/`urllib.request` moved off module level into `rest()` and a new `quote()` helper - lazy import, 0.148 s saved whenever the network is not touched.
2. `xml.etree.ElementTree` dropped from module level; the api key is read with `re.search(r"<apikey>([^<]+)</apikey>")` against the config text, with `ET.fromstring` kept as a lazy fallback if that ever stops matching.
3. New `folders_cached()`: `/rest/config/folders` is cached to `hooks/_folders_cache.json` with `FOLDERS_TTL` = 300 s (env `RECVONLY_GUARD_FOLDERS_TTL`), written atomically via `os.replace`. ⛔ `/rest/db/file` is never cached - that lookup *is* the verdict and changes with every sync.
4. The api key is fetched lazily through a `key_getter()` closure, so a cache hit on a non-mute folder needs neither the key nor the network.

**Measured after, same n=7 median:** path outside any folder **0.445 → 0.129 s** (3.45x) · `claude-home` (sendreceive, the common case) **0.419 → 0.115 s** (3.64x) · `claude-skills` (receiveonly, the lookup is genuinely needed) 0.447 → 0.394 s (1.13x). Write chain **0.87 → 0.57 s**. Weekly: 1.24 h → 0.80 h, **≈26 minutes recovered** - not the "≈3 h" the earlier section implied, because that section's premise was wrong.

**Test:** `~/.claude/hooks/_test_receiveonly_guard_cache.py`, 5 cases, **5/5 green** after the fix and **2/5 green before** it (cases 1-3 red on the unfixed code; cases 4-5 are the regression guards and were green both times by design). Case 4 pins the verdicts of three reference paths against values captured from the original code: `C:/tmp/*` → `(False, None, "путь вне шар Syncthing")`, `~/.claude/hooks/*` → `(False, "claude-home", "шара отдаёт правки наружу")`, `~/.claude/skills/tt/SKILL.md` → `(True, "claude-skills", "файл синкается с флотом, правка тут наружу не уедет")`. Case 5 pins fail-open on a corrupted cache file. A speed-up that changes a verdict is a hole in the gate, not a speed-up.

**What cannot be fixed this way.** Checked the Bash chain for the same cheap win with `python -X importtime` on all 7 python members: heaviest imports are `json` (26-66 ms), `re` (20-42 ms), `pathlib`, `json.decoder` - base modules, all genuinely used. No fat to cut. That chain's 4.50 h/week is 8 interpreter spawns at 0.09-0.20 s each, and it only drops if 8 processes become 1. ⭐ Which means the dispatcher idea from the 2026-11-18 note (`one-dispatcher-for-seventy-hooks`) is the correct fix and now has a number behind it: it targets the 79%, not the 21%.

⚠️ **Instrument lesson, logged.** A single cold run is not a measurement: it disagreed with the 7-run median by 4.5x and shipped. No hook on this node writes its own duration anywhere, which is why a 0.43 s gate survived 69 days while five notes complained about latency. Adding per-hook duration logging is the prerequisite for any further hook optimisation, ahead of the dispatcher.
