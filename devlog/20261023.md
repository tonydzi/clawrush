# 23 October 2026 - dev log

*Engineering events of the day: what was built, what broke, what the root cause was, what got decided.*

## Eleven jobs, three answer keys, and the eight that need a judge

Today's post lists what a new model is tested on before it is trusted with anything: line counting, long instructions, maintaining existing Python, vault memory, retrieval, patching and testing, specialist Q&A, writing posts, outreach in his voice, refusing what it must refuse, and self-assessment. Logged because the list splits cleanly in two and the split decides how much of this can ever be automated.

Three of the eleven have a right answer that a script can check: count the lines, extract the field, hold the instruction and obey the last clause. The rest are judgements. Whether a post sounds like him, whether an outreach message would land, whether a summary kept the point, whether the model's confidence matches its competence, none of those have a key, and a benchmark without a key either needs a human or needs another model as judge. **A test you cannot score is a demo, not a test**, and eight of these eleven are currently demos.

That is not an argument against the list, it is an argument about ordering. The three scorable ones are cheap, repeatable and already built, so a new rail can be rejected in twenty minutes without anyone reading its output. The eight judged ones cost attention, so they belong after the cheap filter rather than instead of it. Running them in the other order is how you end up forming an opinion about a model that cannot count lines.

The measurement gap is the embarrassing part and it is ours. A deterministic suite of fourteen tasks with golden answers written in advance has existed since 17 August; its last real pass on our own rail scored 14 out of 14 and was reproduced immediately, five further passes the same day all scored 14 out of 14. Exactly one run ever happened on a rail that is not ours, and it scored 2 out of 14 on identical tasks. Since that day the suite has fired 561 times in self-test and zero times in anger.

So the number that justifies the whole idea already exists, it is 14 against 2 on the same fourteen questions, and it is two months stale. None of the six models named in the post, GLM, Antigravity, Gemini, Kimi, Meta, Mistral, has been put through it once. Installing a model is an afternoon; running fourteen scored tasks against it is twenty minutes, and it is the difference between a shelf of rails and a routing table.

Open and unmeasured: no pass recorded for any of the six new rails, no scoring method at all for the eight judged categories, no per-task cost figure, and no record of which rail is currently preferred for which job, so model choice stays a config file written by hand.

## Vault memory is the one test another lab cannot copy

Second item from the same post, logged because it is the part that is genuinely ours.

Most benchmark categories in that list are generic: anyone can test line counting or debugging. One is not. Testing whether a model gets it on his second brain specifically, with his distilled sessions and his years of history, is a test that only exists where that vault exists, and it is the only category where a result transfers to nobody else. That makes it the most valuable test in the set and the hardest to build, because the answer key has to be written against private data that keeps changing.

The engineering consequence worth recording: a vault-memory test needs a frozen slice to score against, otherwise today's pass and next month's pass are not comparable. We have never cut such a slice. The retrieval layer is live and the distillates accumulate daily, which is exactly what makes an unpinned benchmark meaningless over time.

Open and unmeasured: no frozen evaluation slice of the vault, no question set with known answers drawn from it, and therefore no way to compare one rail against another on the only dimension that is specific to us.

## The cheapest rail is the newest one, which inverts the obvious cost strategy

Second post of the day reports a result from asking the vendors' own chats what a request costs: the newest model is the cheapest per token, not the dearest. Logged because the intuition it overturns is the one most cost optimisation is built on, and because we have been making the same assumption without ever pricing anything.

The direction checks out on the pair we could verify. Published list prices for the current Opus are 4 dollars per million input tokens and 20 per million output, against 5 and 25 for the previous generation, so the newer model is 20 percent cheaper on both sides, and cache reads dropped from 50 cents to 20. The vendor's own headline figure of roughly 40 percent is measured at default settings with the new model at medium effort against the old one at high, and at maximum effort at least one independent test found no saving. So the rule holds and the discount is a function of how much thinking you buy.

The mechanism named in the post is the part worth keeping: allowances are being cut everywhere while the newest model is priced to be attractive, which is a push rather than a squeeze. **Staying on last year's model to save money is paying a premium for familiarity**, and that is exactly the shape of mistake that survives for months because it feels prudent.

Our own gap here is embarrassing and specific. Yesterday's log already noted that no task has ever been run across our available rails with the same input and the outputs compared. Today adds the second missing column: no token bill per task either. Model choice on this fleet lives in a config file written by hand and judged by feel, so a 20 percent price move in either direction would pass unnoticed.

The cheapest useful artefact is a table with three columns, task, rail, tokens spent, filled from the fourteen scored tasks that already exist. That turns both of today's posts into one decision procedure: the suite says which rails can do the job, the table says which of them is cheapest, and the config stops being an opinion.

Open and unmeasured: no cost-per-task figure for any rail, no record of which effort level our calls actually request (which is the variable the discount depends on), and no alert when a vendor reprices, so the table would be stale the moment it is written unless something rechecks it.
