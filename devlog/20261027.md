# 27 October 2026 - dev log

*Engineering events of the day: what was built, what broke, what the root cause was, what got decided.*

## A seventh machine arrived and our registry still says it does not exist

Today's post describes setting up a newly bought Mac Studio by having the laptop drive it over SSH with Codex doing the work. Logged because it quietly invalidates a record we were treating as current.

**What our registry says.** The fleet holds **six nodes**: a Linux VPS acting as coordinator and source of truth, a Windows GPU hub, a Windows laptop for live interaction, two personal Macs, and a Windows peer belonging to a colleague. On **2 October** a memory note was written in his own words stating plainly that there is no Mac Studio here, after a phantom entry under that name turned out to be a different machine and was removed from the registry by a deployment.

**What today says.** The machine exists, it is bought, it has 128 gigabytes of RAM, and it is being configured right now. So the record is not wrong in the sense of being a mistake; it is **stale**, and the gap between "no such machine" and "a machine being provisioned" is twenty-five days. Nothing in the registry notices a purchase, which is the actual finding: node inventory here updates when a human remembers to update it.

**Consequences that follow from being outside the registry**, and they are specific rather than theoretical. A node that is not in `fleet_nodes.json` gets no vault path profile, no bus address, no heartbeat, and no watchdog. Any routine that iterates the fleet skips it silently. The machine can be fully working and invisible at the same time, which is the same failure shape as everything logged yesterday: a component that is quiet looks identical to a component that is fine.

**On the method in the post, which is sound and worth stating plainly.** The transfer is not a migration, it is a reconstruction: SSH plus an assistant that reads what is on the old machine and recreates it on the new one. That is slower than a disk clone and better in one specific way. A clone carries every accumulated defect across; a reconstruction only carries what is still wanted, and produces a written record of what was installed and why. The cost is that it is long and dull, which is precisely the kind of work that is cheap to delegate and expensive to do by hand.

**The constraint that forced it.** 512 gigabytes of disk on the new machine against a laptop that holds more. No wizard can move a larger disk into a smaller one, so selectivity was not a preference, it was the only option available. The external Thunderbolt drive named in the post is a workaround for a decision already made at purchase.

Open and unmeasured: nobody has measured the laptop by category - vault, sessions, caches, media - so the size of the transfer is unknown and the external drive is being bought against a guess. Also unmeasured: whether the new machine should take over any of the night routines currently crawling on the hub, which was yesterday's complaint and is the obvious use for a quiet machine with 128 gigabytes of RAM.

## The swarm is real machinery, the 1860 hours are not a reading

Second post of the day argues that the tool out of the box is useless, that 1860 hours of sharpening made it an instrument, and that setting it up for someone else makes their instance a member of a swarm that receives everyone's inventions. Logged because two of those three claims are checkable here and one is not.

**Confirmed: Hetzner.** Our fleet registry describes the anchor node as an always-on Hetzner VPS acting as coordinator, source of truth and tie-break, a deliberately thin LLM-free spine. So "I have no DevOps and I sit on Hetzner now" is a literal description of our own infrastructure, not a rhetorical flourish.

**Confirmed: the sharpening.** 279 skills on the shelf of this single node. That is the thing the post calls the difference between a brick and a sharpened instrument, and it is countable.

**Confirmed: the swarm has machinery.** Distribution across nodes is not a promise, it is a layer with its own tooling - a package format, an apply step and a verify step, with portability guards for cross-OS differences. So the sentence "if one member invents something, everyone gets it" describes a mechanism that exists.

**Not confirmed: the hour counter.** There is **no hour counter for Claude on this machine**, searched recursively across nine roots plus PATH under two names. So 1860 hours is his own tally rather than a reading from an instrument, and the 1800 in a later sentence of the same post is the same number recalled differently. The honest framing is a practitioner's estimate, and the post presents it as a measurement ("I keep a counter").

**The gap that matters more than the counter, and it is ours.** Distribution works and the rate is low: **one package went out across the fleet in the last fourteen days**. A swarm whose value is "everyone gets what anyone invents" is worth exactly as much as its shipping frequency, and that frequency is not on any dashboard. Nobody notices a distribution channel going quiet, which is the same failure shape as every silent component logged yesterday: idle and broken look identical.

Cheapest thing that would close it: count packages applied per node per week and put the number where it is seen, so a month of nothing shipping is visible without anyone going to look.

## 242 skills mounted, not copied, and nobody counts which ones the other vendors call

Third post of the day describes several LLMs from different vendors working on one machine out of one folder, sharing one memory and one set of skills that are written to be vendor-neutral. Logged because the central claim is measurable here and it holds.

**Measured today on this node.** The Codex skills directory holds **242 junctions**, each pointing at the same file inside the Claude skills directory, against **279 skills** on the shelf in total. That is the whole of the "unisex" claim made concrete: a skill is one file with two readers, not two copies that drift. The bridge keeping the mounts in place is a live script with its own usage counter, so the mechanism is instrumented rather than assumed.

**Why mounting and not copying matters more than it sounds.** A copy per vendor is the normal shortcut and it fails quietly: the two files diverge, a fix lands in one of them, and the model reading the stale copy behaves differently with no error anywhere. Junctions make divergence impossible by construction rather than by discipline. This is the cheap version of the rule we keep relearning: prevent the failure structurally instead of watching for it.

**The bilingual detail checks out.** Skills here carry Russian and English inside the same file. That is what makes them readable by a stranger's model and why there is no translated copy per vendor to keep in sync.

**The gap, and it is the familiar one.** 242 mounted is a measure of **access, not of use**. Nothing counts which skills the other vendors' models actually invoke, so a skill that no non-Claude reader has ever called looks identical to one that fires daily. Same shape as the distribution rate logged earlier today and the silent components logged yesterday: present and unused is indistinguishable from present and working.

Cheapest fix available, and it is already half built: the bridge has a usage counter, so the missing piece is a per-vendor tally of invocations rather than a new instrument. Thirty-seven skills are also not mounted at all, and nobody has checked whether that is deliberate or drift.

## Two machines, one migration, and the only blocker is the smallest number

Fourth post of the day is written from a six-year-old Intel Mac where half the wanted software will not run, while the first post of the same day described configuring a newly bought Mac Studio with 128 gigabytes of RAM. Logged because read separately those two look like a contradiction, and together they are a clean statement of where the bottleneck actually is.

**Both machines are real.** The Studio arrived recently and is being provisioned from the laptop over SSH; the Intel laptop is where today's work is still happening. Nothing is inconsistent here: this is the middle of a migration, and the daily driver does not change until the new machine is finished.

**The blocker is not the old machine.** It is **512 gigabytes of disk** on the new one against a laptop that holds more, named in this morning's post. That single number is why there is no migration assistant path, why the transfer is selective, why it is being done as a reconstruction rather than a clone, and why an external Thunderbolt drive is now on the shopping list. An Intel processor and a six-year-old chassis are inconveniences; the small disk is the actual constraint.

**On the Intel detail, which is a real software constraint and not nostalgia.** Apple silicon builds became the default for a lot of tooling, and x86 builds lag or disappear. So "half the programs I want to use I cannot use" is a statement about distribution, not about speed, and it does not get better with time, it gets worse. Which makes the migration less of a preference and more of a deadline.

**Fleet consequence, following yesterday's entry.** The registry still holds six nodes and the Studio is not among them. So right now the machine doing the provisioning is in the registry and the machine being provisioned is not, which means any routine that iterates the fleet touches the old laptop and skips the new one entirely. That gap closes when someone adds the node, and nothing will remind anyone to do it.

Open and unmeasured, same as this morning: nobody has measured the laptop by category, so the size of the transfer is unknown and the external drive is being specified against a guess. Also unmeasured: whether the Studio should take over the night routines currently crawling on the hub, which was the complaint logged yesterday and the obvious job for a quiet machine with 128 gigabytes of RAM.
