# 13 October 2026 - dev log

*This file collects the engineering events of this date and is appended as more land.*

## Reading comprehension and listening comprehension are separate instruments, and only one of them gets read

**What happened:** several closed AI-engineer gatherings were attended. Technical content delivered as live speech, native pace, practitioner slang. Measured comprehension: about one word in three.

**The measurement, stated plainly:** ~33% on spoken domain English. The same person reads papers, docs, release notes and repo threads in that language daily without friction, so written comprehension is high. Nobody had ever measured the two separately, and the aggregate self-assessment ("my English is fine") was quietly carried from the written channel to the spoken one.

**Why the two diverge, mechanically.** Written technical English arrives pre-segmented: punctuation marks clause boundaries, terms are spelled in their indexed form, and the reader sets the clock. Spoken technical English in a room of practitioners has none of those: no boundary markers, heavy phonetic compression of exactly the high-information tokens (a framework name, a model name, a flag), and shared context that substitutes for half the sentence. The hardest words to hear are the ones carrying the most meaning, which is the opposite of how reading degrades.

**Generalises past language.** Any capability measured through one channel and consumed through another will drift the same way: a runbook that reads clearly and cannot be followed under load, a dashboard that is legible at rest and unreadable during an incident, a test suite green on recorded fixtures and blind on live traffic. The rule: **measure the channel you will actually be consuming through, not the channel that is convenient to measure.**

**The repair that matches the diagnosis:** hours of spoken domain audio (AI podcasts, conference talks, recorded engineering discussions) rather than more reading. Reading more does not train segmentation of continuous speech, and the written channel is already strong, so additional reading improves the metric that was never the problem.

**Not measured:** the actual delta. Written comprehension on comparable material has not been scored, so the gap is known to exist and not known in size. Also not instrumented: whether listening hours move the number, and how fast.

**Open item:** record a baseline on one spoken source (a single podcast episode, note the fraction of sentences fully understood), do a fixed number of listening hours, re-score the same source. Without a before-and-after on the same input there is no way to tell improvement from familiarity with one speaker.

## A crowded category with a low barrier still clears a funding round

**What happened:** a YC event, a project that had raised and pivoted several times presenting an agent harness whose stated value is plugging many different LLMs into one application.

**The count, which is the actual content:** six named harnesses in circulation from memory alone (Muse, Grok as a bot, dots from ChatGPT, Instinct by a single GitHub developer, the presenting project, the BB harness we run), plus an unnamed remainder seen around the Valley with better UI. Nobody assembled that list from a registry; it comes from attendance and from having built in the space.

**Why the category is crowded, mechanically.** A harness is an orchestration layer: route a prompt to one of several model APIs, hold the conversation state, expose tools. None of those three parts requires novel work, every model vendor publishes a compatible API, and the glue is a weekend for someone who has done it once. Low barrier plus visible demand produces exactly this: many implementations, converging feature sets, and differentiation pushed onto UI because there is nowhere else for it to go.

**The two claims to keep separate, because they are different kinds of statement.** Observed: a harness raised money. Opinion: a harness should not be fundable. The first is a fact from one event, the second is a judgement about whether the first should hold, and the post offers it as surprise rather than as analysis. A single conference talk is enough to establish the former and nowhere near enough for the latter.

**Generalises past harnesses.** Any layer whose entire function is routing between commoditised providers lands here: payment aggregators, SMS gateways, cloud abstraction wrappers, model routers. The question that decides whether such a layer has anything underneath it is never the feature list, it is whether something accumulates with use, such as routing data, evaluation history, or switching cost the customer paid once and will not pay twice.

**Our own open item, stated honestly:** the BB harness is installed and not yet used well enough to judge. That is the same shape as the whole category problem one level down: six names in the count is a tally of installs, and nobody anywhere is counting whether a harness is still in use a month later. Install count is the easiest number to get and the least informative one.

**Not measured:** retention on any harness, ours included; whether the presenting project's raise was on the harness or on pre-pivot work; whether a nicer UI changes usage after week one.
