### ⭐⭐⭐⭐ The store's size has four different public values, and the API contradicts itself

Read today against `api.apify.com/v2/store`, unauthenticated:

| surface | number |
|---|---|
| Apify Store marketing page (per press summary) | **70,000+** |
| API `total` field, request 1 | **121,467** |
| API `total` field, requests 2-5, minutes later | **121,488 → 122,787 → 122,784 → 122,787** |
| API records actually reachable | **13,706** |
| third-party tracker, May 2026 | 25,787 (3,015 publishers, 480,052 MAU) |
| scraper listing, early 2026 | 21,000+ |

The reachable edge was found by binary search over `offset` with `limit=1`: offset 13,705 returns one record, 13,706 returns zero, and so does every offset above it up to 200,000. So the gap between what the API reports and what it serves is **8.9x**.

⚠️ Alternative explanation I cannot exclude: this is a pagination depth cap, not a catalogue size. Many stores cap deep paging. 13,706 is not a round number, which argues slightly against a hardcoded cap, but not decisively. What the cap theory does **not** explain is `total` moving by **1,320 between two requests minutes apart** while the reachable set stayed put. For anyone building against this API the operative number is 13,706, because that is what comes out of it.

⚠️ Also unresolved: whether `total` under a `search=` query is a match count or a global counter. The six platform searches below sum to 32,713, which is 27% of 121,467 and 239% of 13,706 - the second ratio being impossible means `search` results are counted against a different population than the one being served.
