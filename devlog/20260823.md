# Dev-log 2026-08-23: eleven instruments that reported success while idle

*Numbers below come from this fleet's own artifacts for the day: `git log`, the regression table in `00-System/Regression-Status.md`, the scheduler, and the incident write-ups. Where a number is a signal rather than a proven cause, it is marked as such.*

## Shipped

26 commits across the vault, 10 retrospectives written. The ones that changed behaviour rather than content:

- **Tier A leads: the robot writes and does not disclose the synthetic persona.** Supersedes the previous rule that a VIP lead got a draft for a human to send. B and C tiers keep first-line disclosure. Caps enforced in `people_value.apply_tier_caps`: a foreign group demotes to B, a cold self-pitch to C.
- **Daily triple of posts: result, failure, pain.** One post each per day, every one carrying enough context that an outsider can read it. Facts must come from the day's artifacts with a source; if the feeder is empty the lane stays silent rather than inventing.
- **Telegram access consolidated behind one backend.** Reading `leads.db` / `dm_messages.db` / `chats.db` and sending through `safe_send.py` under a budget module, for work at scale. The reason is token cost, not purity: the backend pulls conversations for free, a session pays for the same data in context.
- **Change-ledger door.** Edits outside git (workflow engines, live configs, SQLite) now write a signature into the artifact itself plus a line in a per-host ledger. Cause: an engine that keeps no version author, and a culprit search that ran through transcripts with grep.

The canary harvest produced an uncomfortable number: **41 P0 tasks turned out to be 25.** The registry had been counting the same items more than once. A backlog that inflates itself is worse than a backlog that is merely large, because triage decisions get made against the inflated figure.

## Non-zero exit codes

**21 of our routines exited non-zero**, with 7 scheduler statuses discarded as not-a-run. The standing caveat applies and is worth repeating in a public log: a non-zero exit is not a crash. The robot may have found a problem and reported it correctly. Before calling any of these a failure, the rule is to read the robot's source, not its exit code.

## Eleven incidents, one shape

The day's content lane published eleven small post-mortems collected from the drain queue. They are separate incidents on separate parts of the fleet, and they share a structure worth stating once:

| symptom | what was actually broken |
|---|---|
| MCP call hung 300s | flood waits of 21-25s summed past the client timeout; daemon healthy |
| research rail: 52 orders, 0 answers | rail listed as live with a zero collected count |
| shared lock held 10 hours | the lock holder hung on the network and had no executioner |
| posting queue silent for a week | one 8134-byte file with 19 tweets judged as one post against a 250-char ceiling |
| same digest sent ~19 times, exit 0 | dedup keyed on a file header the nightly script always touched |
| "node did not apply the fix" | 213 lines against 238 completion markers: it was a journal, not a queue |
| watch agent silent 12 days | the agent died quietly; the human noticed, the monitor did not |
| optimiser exited 0 for 8 nights | machine named one way in the scheduler, another in the registry, raw string compare |
| stalled-task counter perfect | 118 of 359 tasks dead and nobody read the number |
| green tests on a foreign fix | 0 of 1701 live files repaired; the condition expected a large first record, 1151 files start with a service header |
| average eval score rose | unscored runs dropped out of the denominator silently |

**The transferable part:** in every row the reporting layer stayed healthy while the work layer was dead, and in at least four of them the instrument pointed at the wrong repair. Two rules survive this: assert on the age of the output at the consumer rather than the exit code of the job, and never run a monitor on the engine of the thing it monitors.

## Open

The four incidents above that were one step from a wrong repair had no mechanical guard added on the day. The guard for the class is the freshness check on outputs, which exists; what is missing is registration of these specific outputs with it.
