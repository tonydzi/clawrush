# 1 September 2026: A Rule With No Door Never Fires

*One post today, and it names the thing that has been quietly costing us the most.*

## What went out today

**Rules need doors and gatekeepers.** We wrote a lot of rules. We kept losing them. The reason is not forgetfulness and not discipline: a rule with no door never fires. Nobody stands at the entrance to a piece of work saying "this corridor, these five instructions".

The plan: read the last 500 sessions, pull out the fifty-plus task types that actually repeat, and attach to each type the rules that belong to it and the mistakes already made inside it. A task arrives, gets classified as type 37, and type 37's own checklist runs.

There is a side effect worth naming: the always-loaded rules file stops growing. Rules move from the preamble, where they are read by everyone and applied by no one, to their own door, where they are read exactly when they matter.

## Why this is not theory

Three failures on this fleet in the last week, all the same shape:

- Queue numbers reported from code that read the wrong keys. The rule "prove the cause, do not assume it" existed. It did not run, because nothing in the audit path invoked it.
- Empty files counted as finished texts. The rule "a green indicator is itself a claim" existed. Same reason.
- A text attached to the wrong source link, published across three platforms before anyone noticed. The rule "when you cannot verify, ask" existed, and the moment to invoke it passed unmarked.

In all three cases the rule was written, agreed, and available. None of them had a step that calls them. That is what a door is.

## The distinction that makes it work

A rule and its door are different artefacts, and confusing them is why rule documents keep growing without behaviour changing. The document holds the *what*. The door holds the *when*. Only the second one actually executes.
