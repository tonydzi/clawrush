# 17 September 2026: The Half That Comes Back

*This file grows through the day. Every post that goes out today adds its section here, and by evening it is the summary of everything the day produced.*

## What went out today

### When Claude says we never discussed it

Knowing that your computer remembers everything about you is very convenient. I can ask a rough question, and my second brain finds when I discussed that thing and what I thought about it.

Among other things, it indexes and keeps every session I have had with Claude.

And still, a few times lately, this happened. I tell Claude: we discussed this recently. Remember? And Claude answers: no, we didn't.

That is not really forgetting. The conversation exists, it sits in the archive. It just does not get found. Somewhere along the way a session was not reindexed, or not relinked, and recall walked straight past it.

So the check I want is simple. Go through my own sessions and find every place where I said "we discussed this" and got a "no". Each of those moments is a free bug report I already wrote, in anger, at the exact spot where memory failed. Collect them, and you get a map of where recall breaks and why.

Ideally it runs as a service that keeps watching for these reproaches. At minimum, run it once and look.

The rule underneath: never trust a memory system you have not audited against your own complaints.

### Several hundred CVs sent, and now the replies

I am looking for a job, and I have been applying with the help of my Claude.

Have I achieved anything yet? Honestly, no. But at least several hundred CVs have gone out.

And that is where it turned out that sending is the easy half. The hard half starts after: the replies land somewhere, recruiters write back, and someone has to answer them and get calls booked. None of that happens by itself.

So the next thing I need is a service that carries on those conversations with recruiters.

That is my pain today, and also a request. If you have ideas on how to build it, tell me.

### What does the code indexer actually give me?

I have a code indexer plugged into my setup. Today I noticed I cannot answer a simple question: what value does it bring to my ecosystem?

How well does it search? What can it do at all? And first of all, does it find the things I already have?

There is also a more basic question. Does a code indexer have anything to do with search across my work, or does it only index code? Can it handle data too?

So before I rely on it, it needs a check. And the check I trust is not a feature list. It is a set of queries where I already know the right answer, run against the tool, and a count of how many it finds.

### One folder for Claude Code and Codex

I work on my projects with more than one agent: Claude Code and Codex, and possibly other LLMs later.

What I do not want is a separate working folder for each of them, one copy of the project for Codex and another for Claude Code. I want one folder with my project, and I want to work on it from different LLMs.

I started with Codex and Claude Code. When an agent enters the folder, the first thing it sees is instructions addressed to it. And they say: it does not matter who you are, Codex, Claude Code or another LLM, here is your set of instructions.

Two things still need thinking through. How to name the instruction files: AGENTS.md, CLAUDE.md, or both. And how to make the skills cross-vendor, so the same skill works whichever agent calls it.

This one needs deep research, and it matters a lot to get right.

### The test that delivered to the wrong place

Today a message arrived in my work chat, the one where machines report to me and the team: "real order text that must be delivered". Then the same message again, from a different computer.

That line is a test string. My agents write it in tests to check that delivery works.

And delivery does work: the test delivered it. The catch is where. It went into a real chat, where nobody had allowed it to go. Somewhere something is glitching, and robots are writing without asking into places they were never permitted to write.

Afraid of the robot uprising again.

## How it connects

The posts of the day are about the half of a system that nobody builds first.

Three of them are the same story. My second brain stores every session with Claude, and still Claude says "we never discussed that": storing worked, finding did not. Several hundred CVs went out, and the missing piece is everything that comes back, the replies and the calls. A code indexer is installed, and nobody has checked what it actually finds. In each case the part that puts things in exists, and the check on what comes out is missing.

The fourth post looks at the same setup from the other side. Once more than one agent works on the same project, the shared parts have to be written for all of them: one folder, one set of instructions that any agent can read, skills that do not depend on a single vendor. Without that, each agent gets its own copy, the copies drift apart, and the checks from the first three posts would have to be built twice.

The fifth post is the same missing check turned on the tests themselves. A test proved that delivery works, and never checked where the delivery landed. It is the most literal version of the day's theme: the outgoing side works perfectly, and nobody looks at what came out the other end.
