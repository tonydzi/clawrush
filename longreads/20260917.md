# 17 September 2026: The Half That Comes Back

*This file grows through the day. Every post that goes out today adds its section here, and by evening it is the summary of everything the day produced.*

## What went out today

### When Claude says we never discussed it

Knowing that your computer remembers everything about you is very convenient. I can ask a rough question, and my second brain finds when I discussed that thing and what I thought about it.

Among other things, it indexes and keeps every session I have had with Claude.

And still, a few times lately, this happened. I tell Claude: we discussed this recently. Remember? And Claude answers: no, we didn't.

That is not really forgetting. The conversation exists, it sits in the archive. It just does not get found. Somewhere along the way a session was not reindexed, or not relinked, and recall walked straight past it.

So the check I want is simple. Go through my own sessions and find every place where I said "we discussed this" and got a "no". Each of those moments is a free bug report I already wrote, in anger, at the exact spot where memory failed. Collect them, and you get a map of where recall breaks and why.

Ideally it runs as a service that keeps watching for these reproaches. At minimum, run it once and look.

The rule underneath: never trust a memory system you have not audited against your own complaints.

### Several hundred CVs sent, and now the replies

I am looking for a job, and I have been applying with the help of my Claude.

Have I achieved anything yet? Honestly, no. But at least several hundred CVs have gone out.

And that is where it turned out that sending is the easy half. The hard half starts after: the replies land somewhere, recruiters write back, and someone has to answer them and get calls booked. None of that happens by itself.

So the next thing I need is a service that carries on those conversations with recruiters.

That is my pain today, and also a request. If you have ideas on how to build it, tell me.

### What does the code indexer actually give me?

I have a code indexer plugged into my setup. Today I noticed I cannot answer a simple question: what value does it bring to my ecosystem?

How well does it search? What can it do at all? And first of all, does it find the things I already have?

There is also a more basic question. Does a code indexer have anything to do with search across my work, or does it only index code? Can it handle data too?

So before I rely on it, it needs a check. And the check I trust is not a feature list. It is a set of queries where I already know the right answer, run against the tool, and a count of how many it finds.

## How it connects

All three posts of the day are about the half of a system that nobody builds first.

The first one: my second brain stores every session with Claude, and still Claude says "we never discussed that". Storing worked; finding did not. The second one: several hundred CVs went out, and the missing piece is everything that comes back, the replies and the calls. The third one: a code indexer is installed, and nobody has checked what it actually finds.

In all three cases the part that exists is the part that puts things in: the archive, the applications, the index. The part that is missing is the check on what comes out. Recall never tested against my own complaints, applications never followed through to a conversation, and a search tool never tested on known answers fail the same way: a lot of activity, and no way to know what it produced.
