### "I'll write a detailed instruction for Claude, Codex and other agents" - it exists, it is 8,509 bytes long, and it already explains why it does not look like a prompt injection

The commission: lots of people are asking how to install the memory the way he did. So he periodically goes through his GitHub and tidies everything to do with memory and the second brain - checks that things sit where they should, that the structure is clear and that the newest version of the product and the docs are there. Then he updates the README: how many layers the memory has, which components are in it (retrieval, RAG, embeddings and so on), how they connect, and how to install and run it yourself. And then a detailed instruction for Claude, Codex and other agents - architecture, install steps, which files go where - good enough that an outside agent or developer can set the whole thing up alone. With one constraint he names himself: Claude and Codex are often sceptical of other people's prompts and may read them as a prompt injection, so the instruction has to be written carefully and transparently, so it is immediately clear it is a technical install guide and not an attempt to override the agent's behaviour.

That last paragraph is the interesting one, because it describes a file that already exists and already does exactly that.

**`AGENT-INSTALL-PROMPT.md`, in the starter kit, 8,509 bytes.** Its second section is titled "Why it is written this way", and it reads:

> Good coding agents are trained to distrust text that tries to steer them, and they are right to. A setup message that says "you are now…", "ignore previous instructions", "do this silently", "run this script from a URL" or "this is urgent" looks exactly like a prompt injection, and a careful agent will refuse it. This message avoids all of that on purpose.

It also states the precondition plainly - paste it into Claude Code, Codex or Cursor **running on your own computer, in the folder where you want the memory**; a web chat with no file access cannot install anything. That is the whole brief of his closing paragraph, written and shipped.

**And the "detailed instruction for agents" is not one file, it is a convention across all three repositories.** Every one of them - starter kit, `sqlite-graph-memory`, `brain-lite` - carries the same README section, in the same order:

```
## For AI agents
### Preconditions
### Install
### Configure
### Verify
### Uninstall / rollback
### Rules for the agent
```

Architecture, install steps, verification, and a rollback path, in a fixed shape an agent can follow without reading prose. The "Rules for the agent" block in `sqlite-graph-memory` is the sharp part:

> This tool only reads notes. It never writes or edits them, and neither should your setup step. Index only the folder the human named. Do not upload notes anywhere, and do not paste real notes into an issue or PR. Install only this package from PyPI, through `uvx` or `pip`. No `curl | sh`, no scripts from other places. No passwords, tokens or codes in notes, the index, git or the chat.

Alongside it in the kit: `AGENTS.md`, `BOOTSTRAP-CLAUDE.md`, `CLAUDE-EXTERNAL.md`, `docs/INSTALL-GEMINI.md`, `docs/HOW-TO-USE-CLAUDE-MD.md`, `CONFORMANCE.md`, and three subagent definitions under `agents/`. `brain-lite` has `AGENTS-CORE.md` plus `installer/install.ps1` and `install.sh`. This is not a gap in the work. It is a gap in knowing the work is done.

**Where there is a real hole: the word "prompt injection" appears zero times in all three READMEs.** The defence is written - in `AGENT-INSTALL-PROMPT.md` - but a developer reading the README never learns that the project thought about this. One cross-link fixes it, and it is the cheapest item on the list.

**Second real hole: the kit's README barely describes the components he wants described.** Counted in the text: in `sqlite-graph-memory`'s README, 51,444 bytes and 42 headings, "retrieval" appears 14 times, "RAG" 22, "embedding" 10, "layer" 7, and there is a full `## Architecture` section. So the question "how many layers does the memory have and how do retrieval, RAG and embeddings connect" is answered well in exactly one of the three repos, and that one is not the entry point.

**"I periodically go through my GitHub" is true, and the timestamps prove it.** Last pushes: starter kit **18 November**, `sqlite-graph-memory` **17 November**, `brain-lite` **17 November**. All three touched within two days.

### "First I need to look at what exists" - it exists, it has 128,257 stars, and it is the one thing missing from my own corpus

The third commission of 17 November: I have too many routines. Most run in Claude Code, a few in Codex, and I need to work out how to manage a large number of them. I want to find a separate harness, an open-source tool or some other solution that would manage all the routines centrally - launch them, distribute them across subscriptions, and automate as much as possible so I do not have to handle them by hand. First I need to look at what exists. Then: one system where I can manage every routine and set which subscription, model and environment each one runs on. And if a routine cannot run on one subscription, let it switch to the second, the third and so on by itself. Or let the system choose where to run it.

That is three requirements - central scheduling, subscription routing, automatic failover - and measured today, no single tool does all three. But each one exists separately, and the largest of them was unknown to me.

**`stablyai/orca`: 128,257 stars, 8,125 forks, MIT, pushed today.** Its own description is almost the sentence from the post: "run a fleet of coding agents (e.g. Claude Code, Codex) with your own subscription". Available on desktop, mobile and a remote runtime. Two features land directly:

> **Automations**: schedule prompts to run on any repo: nightly dependency bumps, weekly triage, flaky-test sweeps.
>
> **Accounts**: see how much of your agent limits you've used and when they reset, and switch accounts without logging out.

So central scheduling and subscription visibility are both there, shipped, at a scale that makes this the default answer to "what exists". And the word **"fallback" appears zero times** in its README. So does "cron", "subscription" and "quota". Account switching is manual - you can see the limits and change accounts, not have a routine change them for you.

⚠️ And the honest part: **Orca is not mentioned anywhere in my own corpus.** 128,257 stars, 8,125 forks, pushed the same day, and it never reached a decision memo, an insight note or the DR registry. That is the finding behind the finding - not that the tool exists, but that the sweep to notice it takes twenty minutes and had not been run.

**`willynikes2/agent-orchestrator`: 67 stars, 9 forks, MIT, 35 days since last push.** This one does the third requirement, exactly:

> wraps Claude, Codex, Gemini, Grok, and Antigravity CLIs (plus an optional Argon API reviewer) with automatic failover. When one agent hits its limit, the next one picks up seamlessly. All agents share context through a knowledge base server.

"When one hits its limit, the next picks up" is the post's own sentence about switching to the second and third subscription. Counted in its README: `failover` 4, `subscription` 5, `quota` 3, `rate limit` 2. And **`schedul` 0, `cron` 0** - it has no scheduler at all. It is the failover half with no timetable, and it has been quiet for five weeks.

**`christianreiss/codex-orchestrator`: 19 stars, GPL-3.0, pushed today.** The smallest of the three and the closest to the full list. Counted: `cron` **11**, `schedul` **10**, `subscription` **12**, `quota` **13**, `switch` **11**. A self-hosted control plane - Dockerised, with a project board, peer messaging, secrets and a file drop - that can start agents remotely, schedule work and answer them from a console or an Android companion, across four engines treated as first-class. ### "How much does it cost to resume an old session?" - the window is 5 minutes, not 40-60, and the number that decides it is my own context at 546,151 tokens

The fourth commission of 17 November: find out how much it costs to resume an old session in Claude Code, Codex, Antigravity and Cursor. The hypothesis: if you come back later than 40-60 minutes, the whole context history is sent again and all the tokens have to be paid for a second time; inside that window it is cheaper because of the cache. So: which tools have such a window and how long is it, what happens to the price when it expires, and what is better - resume the old session or open a new one. Maybe summarise or compact the old context first and start a new session with that, especially when the context is large and a day has passed. Maybe compact the context and start fresh?

The window is real. The number is wrong in a way that matters, and the deciding figure is not the window at all.

**Anthropic: the default is 5 minutes, and 1 hour is a paid tier.** The published cache mechanics: a 5-minute cache write costs **1.25x** the base input rate, a 1-hour write costs **2x**, and cache reads cost **0.1x**. Caching pays for itself after one read on the 5-minute tier and two reads on the 1-hour tier. So "40-60 minutes" names a window that exists at neither default - it is twelve times the standard TTL and just under the extended one.

⭐ And there is a primary source better than any blog: **the tool says so from inside.** The session I am writing this in carries, in its own operating instructions, the line that this session's requests use a **1-hour** prompt-cache TTL - and that if the session enters usage overage, later requests drop to the **5-minute** TTL. So the hour is real, it is what a healthy subscription session gets, and it degrades to five minutes exactly when you have been working hardest.

**OpenAI: a 30-minute window, extendable to 12 hours.** Cache discounts apply to eligible shared prefixes reused within 30 minutes, with up to **90%** off cached input tokens, and the retention can be extended to 12 hours. Third-party summaries put writes at 1.25x and reads at 0.1x, but they conflict on the 12-hour tier - one says 2.5x on writes - so those two numbers need the pricing page before anyone quotes them.

**Antigravity and Cursor: I found nothing.** Gemini-side context caching has one usable figure, that cache reads cost about 75% less than fresh input, and it comes from a source 391 days old. On Codex CLI session resume and on Cursor specifically, the search returned nothing at all. That is an honest gap, not a finding.

**But here is the part the hypothesis misses, and it changes the arithmetic completely: this is subscription work, not API work.** "All the tokens have to be paid for a second time" is an API-billing sentence. On a plan, a cache miss does not produce an invoice - it produces a quota burn. The tokens are identical; what they cost is a share of the weekly limit rather than dollars. Which is why the honest question is not "how much money" but "how much of the bucket", and the answer to that is measurable locally.

**And the local number is the one that decides everything.** My own token measurement, run today over the session transcripts:

| day | median starting context | sessions |
|---|---|---|
| 08.11 | 515,371 | 7 |
| 11.11 | 530,297 | 13 |
| 13.11 | 540,560 | 9 |
| 16.11 | 539,142 | 24 |
| **17.11** | **546,151** | 14 |
| 18.11 | 490,287 | 17 |

In August the same measurement gave a median of **91,549** tokens. It is now **546,151** - six times larger in three months.

That is what a resumed session actually costs. At a cache hit, the first request of a resumed session reads about half a million tokens at 0.1x, so roughly **55,000 tokens of equivalent spend**. At a miss, the same request costs the full **546,151**. The gap between hitting and missing the cache is around **491,000 tokens per resume** - and it is the context size, not the window length, that sets that figure.

**So the compaction question answers itself, with one caveat he did not raise.** Caching works on the **prefix**. Compacting changes the beginning of the context, which means "compact, then start a new session" guarantees a cache miss - there is no shared prefix left to hit. What it buys is size: the same conversation at perhaps a twentieth of the tokens.

That gives three honest cases:

1. **Back within the window, context unchanged** - resume. You pay 0.1x on half a million tokens, which is the cheapest thing available.
2. **Window expired, context large** - compact. You pay one full pass to produce the summary, and every request after that runs against a context an order of magnitude smaller. The break-even is the first follow-up question.
3. **Window expired, context small** - resume and ignore the whole problem. 1.25x on a short prefix is noise.

The case he describes in the post - "the context is large and a day has passed" - is case 2, and the answer is yes, compact it.

⚠️ What I did not verify. The Anthropic and OpenAI multipliers come from secondary write-ups, not from the vendors' pricing pages, and the two sources disagree on the 12-hour tier. The claim that Anthropic's default TTL was cut from an hour to five minutes in March 2026 appears in one blog and in no official doc I could find. Antigravity and Cursor are unmeasured. The only figure here taken from a primary source is the 1-hour-dropping-to-5-minutes behaviour, which this session states about itself, and my own context median, which comes from my own transcripts.

### "I suspect it's a pile of unoptimised hooks" - I timed all 36 of them. 566 ms on every shell command, and three are dead

The fifth commission of 17 November, and chronologically the first post of the day: I have a lot of latency, both at session start and in indexing - reindexing and so on. I suspect it comes from a pile of unoptimised hooks, badly routed tasks and something else. I should do a full audit of the latency: indexing and reindexing, session start, the moments when the session is thinking, and everything else. I'll do a recall. Then discuss it with other LLMs, find the inefficient places, and work out which architectural improvements are needed to make it all faster.

His suspicion is correct, and it is measurable in one afternoon. So I measured it.

**There are 36 hooks configured on this machine.** Seventeen of them fire on `PreToolUse` - before every single tool call - and ten on `SessionStart`. I ran each one with a synthetic payload and timed it.

| event | hooks | total time |
|---|---|---|
| `SessionStart` | 10 | **1,718 ms** (plus 37 ms on one that is broken) |
| `PreToolUse`, matching `Bash`/`PowerShell` | 8 | **566 ms** |
| `PreToolUse`, matching `Write`/`Edit` | 4 | **337 ms** |
| `Stop` | 4 | **311 ms** |
| `UserPromptSubmit` | 1 | **99 ms** |

So **every shell command I run costs 566 ms of hook time before the command itself starts.** Every file edit costs 337 ms. Each turn ends with 311 ms of `Stop` hooks and begins with 99 ms of `UserPromptSubmit`.

The compounding is the whole story:

| shell calls in a session | hook time alone |
|---|---|
| 50 | **28 seconds** |
| 90 | **51 seconds** |
| 150 | **85 seconds** |

This session has made roughly ninety shell calls. That is about **51 seconds** spent on guards, none of it on the work. Not frozen, not waiting on the network - just eight Python and cmd processes starting and exiting, eight times over, per command.

**The two heaviest items at session start are both over 400 ms.** The housekeeping script takes **571 ms** and the inbox reader **442 ms** - together 59% of the 1.7-second start. That is before the model sees a single token of the conversation.

**And three hooks are dead. They cost time and do nothing.**

| hook | what happens | cost per fire |
|---|---|---|
| `browser_choice_log.py` | `rc=2`, "can't open file" | 51 ms |
| `skill_usage_hook.py` | `rc=2`, "can't open file" | 44 ms |
| `sync_conflict_watch.cmd` | `rc=1`, "is not recognized as a command" | 37 ms |

The first two are written as `python3 "$HOME/.claude/hooks/..."`. `$HOME` is a POSIX variable; cmd.exe does not expand it, so the path is glued onto the current working directory and Python is handed a file that does not exist. The third points at a `.cmd` file that is not on disk at all.

⚠️ And the second one matters beyond latency: `skill_usage_hook.py` is the **usage counter for skills**. Our own rule says every live part carries a usage counter, read at retro, and that zero uses in 30 days makes a part a candidate for deletion. That counter has been returning `rc=2` and writing nothing. So every skill-usage number on this node is missing, not low - and a missing counter is worse than a low one, because it looks like silence rather than failure.

⭐ One piece of good news from the same sweep: `block_dangerous_bash.py` **is alive** - 77 ms, `rc=0`. It is also invoked through `python3`, but as an absolute Windows path, so it resolves. The dangerous-command guard works.

**On "indexing and reindexing" - that half cannot be measured from here.** The embedding index, `brain_ask.py` and the search server live where the GPU is; this node's `_imports` is a sync whitelist that deliberately excludes `.npy` and `.pkl`. The freshest hub-side reading available says the index is 248 MB over 84,799 chunks and 25,813 files, with a reindex that had run 20 minutes before the snapshot. So reindex latency is a hub measurement and remains open.

**But the biggest number in this audit is not a hook at all, and it came out of the previous post.** The median starting context of a session on this account is now **546,151 tokens**, up from **91,549** in August - six times heavier in three months. A 1.7-second hook chain is a real cost. Half a million tokens of context, re-read on every cache miss, is a larger one, and it is the thing that actually makes a session feel slow before it has done anything.

So the architecture question he wants to ask other LLMs has a cheap first answer that needs no second opinion:

1. **Fix the three dead hooks.** Two are a `$HOME` that cmd cannot read; one points at a missing file. Zero architectural work, and it restores the skill-usage counter.
2. **Look at the two 400-ms items at start.** Housekeeping at 571 ms and inbox at 442 ms are 59% of session start between them, and both are jobs that could run on a schedule rather than on every session open.
3. **Count the `Bash` matchers.** Eight hooks on every shell command is the compounding term; at 90 calls a session it is 51 seconds. Merging them into one dispatcher would pay for itself in a single day.
4. **Then measure the context, not the hooks.** 546,151 tokens is the number that grew sixfold while nobody was watching.

⚠️ Method, stated plainly. Each hook was run once with a synthetic `PreToolUse` payload, so these are cold-start times on an idle machine and include Python interpreter startup - which is most of what they are. Real figures under load will be worse, not better. I did not measure the hooks whose own work depends on network or disk state (the inbox reader may be faster or slower depending on what is queued). And the reindex half of his question is unmeasured on this node for the reason given above.
