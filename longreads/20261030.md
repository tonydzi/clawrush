## What went out today

### Muse in the CLI or not, and what a token actually costs

**He asked whether Muse has a CLI. It left beta two months before the question.**

The request: Meta shipped a new LLM called Muse, and the open questions are practical ones. Is it in the CLI, meaning can you actually drive it from a terminal? What does a token cost? Can you run deep research on it? Does it have a proper app the way Claude Code or Codex do? So far the only visible thing is that it has a pile of connectors, which probably makes it a neat piece inside the Facebook ecosystem. And a direct ask to anyone already using it: tell me how.

Four of those five have public answers, so here they are in order.

**Is it in the CLI.** Yes, and not recently. **Muse Code**, Meta's terminal coding agent, went into beta on **5 August 2026** and left beta on **31 August 2026**. Muse Spark 1.3 has been selectable inside it since **2 September**. The CLI itself is free to install and you pay only for the model underneath. So the question "is it in the CLI" had an answer roughly two months before it was asked, and the answer was sitting in public documentation the whole time.

**What a token costs.** Muse Spark runs about **$1.25 per million input tokens**, **$4.25 per million output**, and **$0.15 per million cached input**. Muse Wonder is the expensive tier: **$4 in, $20 out, $0.20 cached**, plus roughly **$2.50 per 1,000 web search queries**. New accounts reportedly get **$20 in starter credit**. ⚠️ Every one of those figures comes from third-party guides, and one of those guides states plainly that Meta has not published an official pricing page. Treat them as provisional and check `dev.meta.ai` before budgeting against them.

**Deep research on it.** No. Not one source describes Muse as a deep-research agent. Muse Code is a coding agent in a terminal, which is a different animal. Muse Wonder does have web search as a billable line item, but a search call is not a research pipeline.

**An app like Claude Code or Codex.** That is exactly what Muse Code is: a multi-agent terminal agent, the direct structural analogue. The API is also OpenAI-compatible, so an existing client usually just needs a new base URL and key. Simon Willison shipped an `llm-meta-ai` plugin within hours of the API going live.

**And Europe, where his guess was right.** The consumer Muse app **skips Europe**: it is limited to the US and Canada, and Meta has announced no European date. For the API and the CLI, Meta has published no country list at all, and developers in Canada and Australia have reported the contributor tier failing for them with no response either way. So "available to Americans, unclear for Europe" is an accurate read, and the uncertainty belongs to Meta rather than to him.

**Now the part that is about us, and it is the uncomfortable half.** He asks what a token costs on a model he does not have. Here is what we can say about the tokens we are already paying for.

The routing table carries **six rails**: Claude (Anthropic Max, **$200/mo**), Codex (ChatGPT Pro, **$200/mo**), Gemini (**$20/mo**), GLM Coding Pro (**$16/mo**), Grok (SuperGrok, **$300/mo**), and Mistral, which has no subscription at all and runs piecewise through OpenRouter. That is **$736 a month** of standing commitments across eleven classes of work.

**Of those six, the tank can be read by machine on exactly one.** Codex, where the remaining quota comes out of a rollout log. For the other five the field says `quota_readable: false`, and for Claude the note is blunt about it: there is no machine way to get the percentage, the only signal that the tank is empty is the phrase "usage limit reached" appearing in a transcript. The most expensive rail of the six, Grok at $300, carries its own note: highest price, lowest utilisation.

**Two more things the table knows about itself.** GLM's subscription was bought on **5 August** and the key was only obtained on **22 September**, seven weeks of a paid rail with no door into it. And the work classes reference two rails, `agy` and `mayak`, that are not declared in the rails section at all, so a fallback chain can point at a name the table cannot resolve.

**On our side Muse appears nowhere.** Zero mentions across the skills, zero in the vault's concepts, insights and resources, zero in the routing table. The only place the word shows up by substance is a line inside a third-party repository description in one of our registries.

**The thing worth copying.** Before adding a seventh rail, read the fields on the six you already pay for. A public price list you can look up in a minute is a smaller problem than your own bill being unmeasurable on five vendors out of six.

### Screenpipe is letting me down, and the licence answered a question he did not ask

Anton's recorder is failing him, so he asked for a replacement: something open-source, running on Mac and Windows, listening continuously to everything on the computer and writing audio only, no video. Environmental audio. And he added the part that makes it a real request: he does not want to write any of it himself.

Then two more questions. What do people actually complain about in Screenpipe? And is Screenpipe genuinely open-source, or are the parts you would need to fix locked inside binaries?

The last question has the sharpest answer, and it is not about binaries at all.

**Screenpipe is no longer open-source, and the barrier is legal rather than technical.** The repository says "source-available" and ships a file titled **Screenpipe Commercial License**, copyright **Negentropy Labs, Inc. (dba Screenpipe)**. Personal and non-commercial use is permitted; commercial use "requires a paid Screenpipe Enterprise plan and a commercial license from the Licensor expressly covering that use," with a 7-day commercial evaluation. The clause that matters for his question is this one: the license "governs the source code of the Licensed Work and any binaries built from it by you or by third parties." So you can read the code, you can patch the code, you can compile it, and none of that buys you the right to run the result commercially. Official prebuilt builds are not even covered by that license, they fall under the Terms of Service plus your subscription.

Versions released before the change stay MIT. That line is the only open-source left in the project, and it points backwards.

**Why it changed is visible in the repository title: `screenpipe | YC S26`,** tagged `ycombinator`. The desktop app now carries Free, Basic and Business plans, Enterprise is priced per deployment, and new lifetime licenses are no longer sold while old ones stay valid. A product went through an accelerator and the licence followed. Marketing pages across the web still describe it as MIT, which is the part worth knowing: the public story and the LICENSE file disagree, and the LICENSE file wins.

**What people complain about, with issue numbers.** The oldest famous one is **#183**: CPU over 100%, memory over 10GB, and the settings page still reporting "healthy" while that happened. **#278** is a **$300 bounty** on a memory leak, target "24 hours under 6 GB", actual behaviour quoted in the issue as 8GB after 30 minutes and 20GB after 20 hours, with ffmpeg and SQLite named as suspects. **#7059** is recent, roughly 46 days old: Windows desktop sluggishness and cursor lag while recording, CPU around 28%, the process at about 1.6GB and **over 300 threads**. **#1202** reports `screenpipe pipe info` returning a response-decoding error, which is the closest thing to his "broken API". The README advertises 5-10% CPU. ⚠️ Issue status varies and some of these may be fixed in later releases, so treat them as reported rather than current.

**Now our own side, which is the part he lived through.** On **28 September** a Screenpipe update moved its database to a new file. Our watchdog kept reading the old one, where nothing changes, and kept reporting fine. Underneath, audio transcription had been stalled since **27 September 13:30**, over a day: one process hung on a read, the database could not flush, and the queue grew to **60,000 pages**. He sat down to write a follow-up after an important call and the call was simply not in the recording. Fireflies had been recording in parallel and that is the only reason the transcript existed at all. Two days later, on **30 September**, the audio rail went quiet for **5.4 days** while health still said "active".

⭐ Put our two incidents next to issue #183 and the same defect appears in both: the number was wrong and the indicator said healthy. We did not discover a Screenpipe quirk, we hit the same class their own bug tracker has been carrying since 2024. That is the strongest argument for replacing it, and it is stronger than any of the performance complaints.

**On the replacement, the honest answer is that the thing he described does not exist ready-made.** The closest fit is **Meetily** (`Zackriya-Solutions/meeting-minutes`): licence line reads "MIT License - Feel free to use this project for your own purposes", installers for Windows x64 and macOS aarch64, Linux by building from source, and capture that is **audio only**, described as microphone and system audio simultaneously with ducking and clipping prevention. Transcription runs on-device with Whisper or Parakeet. Two caveats decide whether it is usable: the project is built around **meetings**, not ambient capture, and its page does not claim always-on recording; and summaries default to offering cloud providers, so that has to be pinned to local Ollama or the audio leaves the machine.

The rest of the field is narrower, not wider. Parrot is macOS only. whisper-stream is a bash script with silence detection, not a daemon. OpenRecall captures screenshots, not audio. Microsoft Recall records no audio at all.

So "I do not want to write any of it myself" collides with a real gap: continuous ambient audio, cross-platform, under a licence that survives commercial use, is not a product anyone is shipping. The available choices are a meeting tool pressed into ambient duty, an old MIT snapshot of Screenpipe that no longer gets fixes, or writing the daemon. The deciding question is not which tool is best, it is whether ambient capture was ever the requirement or whether calls were.

And one instrument rule, from both his incidents and theirs: a recorder's own health page is not evidence that recording happened. The only proof is the age of the newest transcript.

## How it connects

Both posts of this date turn out to be the same complaint about instruments, approached from opposite ends.

The first one asks what a vendor charges and what our own six rails cost us, and the answer is that remaining quota is machine-readable on exactly one rail of six. There is no indicator, and the absence is visible.

The second one is worse, because the indicator exists and lies. Screenpipe's own health page reported fine while transcription had been stalled for over a day and while the audio rail was silent for 5.4 days, and the same shape sits in their bug tracker as issue #183 since 2024: CPU over 100%, memory over 10GB, settings page still saying "healthy". Next to it, a second claim that nothing verified: pages across the web still advertise the project as MIT while its LICENSE file has become a commercial one.

So the day's lesson is narrower than either post. A missing indicator makes you ask the question. A confident wrong indicator stops you from asking it, and costs a recorded call.
