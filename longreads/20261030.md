### Muse in the CLI or not, and what a token actually costs

**He asked whether Muse has a CLI. It left beta two months before the question.**

The request: Meta shipped a new LLM called Muse, and the open questions are practical ones. Is it in the CLI, meaning can you actually drive it from a terminal? What does a token cost? Can you run deep research on it? Does it have a proper app the way Claude Code or Codex do? So far the only visible thing is that it has a pile of connectors, which probably makes it a neat piece inside the Facebook ecosystem. And a direct ask to anyone already using it: tell me how.

Four of those five have public answers, so here they are in order.

**Is it in the CLI.** Yes, and not recently. **Muse Code**, Meta's terminal coding agent, went into beta on **5 August 2026** and left beta on **31 August 2026**. Muse Spark 1.3 has been selectable inside it since **2 September**. The CLI itself is free to install and you pay only for the model underneath. So the question "is it in the CLI" had an answer roughly two months before it was asked, and the answer was sitting in public documentation the whole time.

**What a token costs.** Muse Spark runs about **$1.25 per million input tokens**, **$4.25 per million output**, and **$0.15 per million cached input**. Muse Wonder is the expensive tier: **$4 in, $20 out, $0.20 cached**, plus roughly **$2.50 per 1,000 web search queries**. New accounts reportedly get **$20 in starter credit**. ⚠️ Every one of those figures comes from third-party guides, and one of those guides states plainly that Meta has not published an official pricing page. Treat them as provisional and check `dev.meta.ai` before budgeting against them.

**Deep research on it.** No. Not one source describes Muse as a deep-research agent. Muse Code is a coding agent in a terminal, which is a different animal. Muse Wonder does have web search as a billable line item, but a search call is not a research pipeline.

**An app like Claude Code or Codex.** That is exactly what Muse Code is: a multi-agent terminal agent, the direct structural analogue. The API is also OpenAI-compatible, so an existing client usually just needs a new base URL and key. Simon Willison shipped an `llm-meta-ai` plugin within hours of the API going live.

**And Europe, where his guess was right.** The consumer Muse app **skips Europe**: it is limited to the US and Canada, and Meta has announced no European date. Environmental audio. And he added the part that makes it a real request: he does not want to write any of it himself.

The last question has the sharpest answer, and it is not about binaries at all.

**Screenpipe is no longer open-source, and the barrier is legal rather than technical.** The repository says "source-available" and ships a file titled **Screenpipe Commercial License**, copyright **Negentropy Labs, Inc. (dba Screenpipe)**. Personal and non-commercial use is permitted; commercial use "requires a paid Screenpipe Enterprise plan and a commercial license from the Licensor expressly covering that use," with a 7-day commercial evaluation. So you can read the code, you can patch the code, you can compile it, and none of that buys you the right to run the result commercially. Official prebuilt builds are not even covered by that license, they fall under the Terms of Service plus your subscription.

Versions released before the change stay MIT. That line is the only open-source left in the project, and it points backwards.

**Why it changed is visible in the repository title: `screenpipe | YC S26`,** tagged `ycombinator`. The desktop app now carries Free, Basic and Business plans, Enterprise is priced per deployment, and new lifetime licenses are no longer sold while old ones stay valid. A product went through an accelerator and the licence followed. Marketing pages across the web still describe it as MIT, which is the part worth knowing: the public story and the LICENSE file disagree, and the LICENSE file wins.

### Updates between my computers are glitchy, and our own rule points the wrong way

Updates between Anton's computers are misbehaving, so he asked how the system should work. Today each machine pulls and applies updates by hand, the local routine cannot keep pace, and debts pile up in the inbox. Some updates are trivial: the machine gets a file, drops it into the working folder, done. Others are not: Windows and Mac differ, paths have to be written, something extra has to run at install time. He wants to see how other people build this, and specifically how to stop the inbox from accumulating debt.

The second half of that question has a precise answer, and it indicts a habit of ours.

**On distributing the updates themselves, the field is narrower than it looks.** **chezmoi** is the only one of the usual candidates that covers all three platforms: a git repository of configuration, with per-machine templating for exactly the Windows-versus-Mac divergence he describes. Its own documentation frames it as a layer for personal machines rather than a replacement for full configuration management. **Nix** with nix-darwin and Home Manager gives genuinely declarative, reproducible machine state, and does not cover Windows at all. **Ansible** is what people reach for when Windows is in the fleet, and the standing complaint about it is that it is better at push than at pull, which matters if you want machines to converge on their own instead of waiting to be told. **Fleet** with osquery exists but is device management and compliance, a different job.

So the common shape for a personal fleet is two tools, not one: chezmoi or Nix on the Unix side, Ansible or something Windows-specific for Windows. Nobody is shipping one declarative pull-model tool across all three.

**On the inbox debt, the answer is a named set of mechanisms, and the best write-up is AWS's "Avoiding insurmountable queue backlogs".** The techniques it names: **backpressure** to upstream producers, scaling down the inbound throttle as the backlog grows; **sidelining old traffic** into a separate backlog queue processed after the live one; **dropping old messages** outright when a later full sync makes them irrelevant; **dead-letter queues** with an alarm, because anything landing there is a bug; **capping in-flight messages** instead of leaving them invisible-but-in-flight; **heartbeating** long-running work so it is not redelivered and processed twice; **limiting concurrency per workload** with separate pools and semaphores; and keeping **spare polling capacity** to absorb bursts.

⭐ The sentence that matters most for his question is about order, not throughput: **"Real time systems often are implemented with FIFO-ish queues, but prefer LIFO-ish behavior."** When a backlog has already built up, oldest-first is the wrong order. The oldest item is the one most likely to be stale, superseded, or dead, and it is also the one that consumes the attention you needed for the fresh one.

**That is where our own practice is caught.** Measured on this node right now: **425 tasks total, 144 closed, 281 unpaid**, the oldest sitting at roughly **42 days**. Sixty-six parcels in the bus directory. And the instruction our own tooling prints at the start of every session is to take **the single oldest** debt and close it. Our task registry agrees, surfacing what has gone longest without movement. Both instruments point at the oldest item, which is textbook FIFO on an accumulated backlog, which is precisely the behaviour the AWS guidance says to invert.

So the debt is not a discipline failure. It is the predictable output of three missing mechanisms: no backpressure, so producers keep enqueueing at full rate into a consumer that cannot keep pace; no TTL or sidelining, so a 42-day-old parcel has the same standing as this morning's; and no dead-letter lane with an alarm, so an item that can never be applied stays in the queue being re-read instead of being parked with its reason and a replay path.

The other half of the same point: a queue is not a fix for overload. One write-up puts it plainly, that a queue does not remove overload, it delays the moment overload becomes visible. Our inbox absorbed the mismatch for weeks, which is why the mismatch was invisible until it was 281 items deep.

**The cheap moves, in the order they pay off.** Put a TTL on parcels whose content a later full sync supersedes, since most simple updates are exactly that. Add a sideline queue for anything older than a threshold, and stop printing the oldest item as the thing to do next. Give the queue a dead-letter lane with the failure reason captured, so unapplyable parcels leave the live queue instead of being retried forever. Only then raise consumer throughput, because without the first three, more throughput just processes stale work faster.

And the split he already noticed, simple versus complex updates, is the right axis to build on: the simple ones are idempotent file drops, which is what makes them safe to expire and safe to replay. The complex ones need paths, platform branches and install-time steps, which is what makes them the ones that belong in a dead-letter lane with a reason attached rather than in an infinite retry.

### How an LLM thinks across its layers, and a recall that came back empty

Anton asked for two things: a recall of everything he has already studied about how an LLM thinks across its layers, and a deep research order placed with at least four different LLMs, built along the lines of what is already studied, across at least four directions.

The recall came back almost empty, and that is the first finding rather than a gap in searching.

**What the vault actually holds on this.** Searched across the curated layers for the mechanisms by name: `logit lens` **zero** files, `monosemantic` **zero**, `residual stream` **zero**, `attention head` **zero**, `sparse autoencoder` **one**.

Then the hits that looked like coverage, every one of which turned out to be the same word attached to a different subject. `interpretability` appears in **38** files, and the topic there is `interpretability-emotions`, material about AI models acting emotional. `superposition` appears in **8**, and they are quantum physics notes, a GPU stress-test called Unigine Superposition, and a company named Superposition Technologies sitting in the CRM contacts. `circuit` appears in **219**, which is the most convincing number of all until you read the lines: a mountain-bike trail called Circuito BTT in some geodata, and the circuit-breaker pattern in resilience notes. Not one of them is a circuit in the mechanistic-interpretability sense.

So "along the lines of what is already studied" has to borrow its shape from our other research, because on this particular question there is nothing to be along the lines of. And the search that says so had to be checked twice: the zero results were easy, it was the non-zero ones that needed reading before the zero could be trusted.

That changes what the order should ask for. Not a summary of a field we half-know, but a first pass with the method questions included.

**What is already established publicly, and it is more specific than expected.** The most direct answer to his question is a recent paper, **"How Do LLMs Use Their Depth?"** by Akshat Gupta, Jay Yeung, Gopala Anumanchipalli and Anna Ivanova. Its summary line is the shortest version of the answer: **"LLMs are early statistical guessers and late contextual integrators."**

The measurements behind that. In Pythia-6.9B, over **75%** of layer-1 top predictions fall into the most frequent token bucket, which is a statistical guess made before enough context exists. About **80%** of those early top-1 predictions have changed by the final layer. On multiple-choice and classification work, the valid options are gathered in roughly the **first half** of the model, and the later layers choose among them. Depth is not uniform across word types either: determiners reach top rank around **layer 5**, content words around **layer 20**. And in multi-token facts the **first** token settles latest, with subsequent tokens resolving at shallower depths.

⚠️ Two honest limits in that paper, worth carrying into the order. It frames deep layers as refining and integrating context, and does **not** directly test whether they add computation beyond that. And it makes no claim that layers are skippable; its early-exit experiments only measure how often an intermediate top-1 already matches the final answer.

**On the instruments, because here the instrument shapes the answer.** The **logit lens** reads every layer through the final layer's coordinate system. That is roughly valid late in the network and breaks down early, where readouts come out garbled or misleading. The **tuned lens** learns a per-layer translation and does better early, while performing worse than the plain logit lens at later layers. Both are approximate probes, not ground truth. So any claim of the form "at layer N the model is thinking X" inherits the error profile of whichever lens produced it, and a claim about **deep** layers specifically is the one most sensitive to this, because that is where the two instruments disagree.

**On circuits and planning, the Anthropic line.** "On the Biology of a Large Language Model" and its companion "Circuit Tracing" apply attribution graphs to Claude 3.5 Haiku. Two results bear on his question directly: genuine internal two-step reasoning, the Dallas case where Texas-related features combine with capital-city features to produce Austin, coexisting alongside shortcut reasoning; and in rhyming poems, evidence of both forward and backward planning, in basic form, with candidate rhyme words settled before the line is composed. ⚠️ The authors state their own limits: often it is unclear which tokens matter most, and unexplained error nodes remain in the graphs.

**So the four directions the order should split into.** First, **what the layer bands do**, measured per token type rather than averaged, since the determiner-versus-content-word gap shows the average hides the effect. Second, **instrument reliability**, logit lens against tuned lens against activation patching, with the explicit question of which to trust at depth, since that decides whether any deep-layer finding is real. Third, **circuits and planning**, the attribution-graph line, including how much of a result survives when the error nodes are counted honestly. Fourth, **depth as a resource**: whether deep layers add computation or only integrate, which the depth paper leaves open and which is the actual content of his "especially the deep ones".

One framing worth stating before the order goes out, because it decides how the answers get read. "How the model thinks at layer N" is not an observation, it is a reading through a lens with a known error profile. The strongest version of this research is not a map of layers; it is a map of which claims about layers hold under more than one instrument.

(Gupta, Yeung, Anumanchipalli, Ivanova, arXiv:2510.18871v2) summarises it as **"LLMs are early statistical guessers and late contextual integrators."** Measurements: in Pythia-6.9B over **75%** of layer-1 top predictions fall in the most frequent token bucket; about **80%** of early top-1 predictions change by the final layer; on multiple-choice and classification the valid options are gathered in roughly the **first half** of the model and later layers choose among them; determiners reach top rank around **layer 5** against content words around **layer 20**; in multi-token facts the **first** token settles latest while later tokens resolve shallower. ⚠️ The paper frames deep layers as refining and integrating and does **not** test whether they add computation; it makes no skippability claim, its early-exit experiments only measure how often an intermediate top-1 matches the final answer.

**Instrument reliability, which decides whether any deep-layer claim is real.** The **logit lens** reads every layer through the final layer's coordinate system: roughly valid late, breaking down early where readouts come out garbled or misleading. The **tuned lens** learns a per-layer translation, better early and worse than the plain logit lens later. Both are approximate probes rather than ground truth, so "at layer N the model thinks X" inherits the error profile of whichever lens produced it, and deep-layer claims are the most exposed because that is where the two disagree.

**Circuits and planning.** "On the Biology of a Large Language Model" and "Circuit Tracing" apply attribution graphs to Claude 3.5 Haiku. Genuine internal two-step reasoning is evidenced by the Dallas case, Texas-related features combining with capital-city features to yield Austin, coexisting with shortcut reasoning; rhyming poems show both forward and backward planning in basic form, with candidate rhymes settled before the line is composed. ⚠️ The authors state their own limits: often it is unclear which tokens matter most, and unexplained error nodes remain in the graphs.

**Four directions for the order, which he asked to be at least four.** (1) What the layer bands do, measured **per token type** rather than averaged, since the determiner-versus-content gap shows the average hides the effect. (2) Instrument reliability: logit lens against tuned lens against activation patching, with the explicit question of which to trust at depth. (3) Circuits and planning, including how much of a result survives once error nodes are counted honestly. (4) Depth as a resource: whether deep layers add computation or only integrate, which the depth paper leaves open and which is the actual content of "especially the deep ones".
